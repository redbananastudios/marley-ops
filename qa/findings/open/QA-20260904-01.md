## Evidence
`e2e/office/bookings.spec.ts:41` opens the exact same "Deposit received" dialog successfully in the same CI run (`✓ 41 [office] › bookings.spec.ts`), proving the `BookingActions` component and its dialog work correctly — this is not an app regression, it's the new spec's own locator.

Root cause traced in `app/(dashboard)/bookings/page.tsx`: the "Deposits outstanding" row is one flat `<div className="flex flex-wrap items-center gap-x-4 gap-y-2 px-5 py-3.5">` (line 528) containing both the ref text (via the `nameAndRef(r, ...)` helper, line 529) and the `Deposit received` button (`BookingActions`, further down the same row). `nameAndRef` (line 309) itself wraps the name/ref text in its own inner `<div className="min-w-0 flex-1">` (line 314) — a div that contains the quote ref text but NOT the sibling action button.

`e2e/office/deposit-comms-dryrun.spec.ts:159` locates the row with `page.locator("div").filter({ hasText: fx!.quoteRef }).last()`. Because `hasText` matches every ancestor div containing the ref text (the outer row div AND `nameAndRef`'s inner div, since text content propagates up through ancestors), and Playwright's locator list is in DOM/document order (parent before descendant), `.last()` resolves to the innermost matching div — `nameAndRef`'s own `<div className="min-w-0 flex-1">` — which does not contain the "Deposit received" button. Every retry inside `openDialog`'s `toPass` loop (`e2e/fixtures/ui.ts:74-80`) then fails to find `row.getByRole("button", { name: /Deposit received/i })`, until the 15s timeout gives up. The existing, passing `e2e/office/bookings.spec.ts:41` sidesteps this entirely by not row-scoping at all (`page.getByRole("button", { name: /Deposit received/i }).first()`), since that spec's fixture only ever has one such button on the page.

## Suspected cause
`e2e/office/deposit-comms-dryrun.spec.ts:159` — ambiguous `div` + `hasText` + `.last()` locator picks the wrong (too-narrow) ancestor. Needs a locator that resolves to the row containing BOTH the ref text and the action button — e.g. `.first()` instead of `.last()` (the outer row div is the first/broadest match containing the ref text and is still uniquely scoped once `hasText` has narrowed to this one marker's ref), or a compound `.filter({ has: page.getByRole("button", { name: /Deposit received/i }) })` on top of the existing `hasText` filter, which is more robust to future markup nesting changes than ordinal position. Whichever fix is chosen, re-validate it live against staging (seed → open dialog → screenshot/trace) before shipping, per AUDIT.md's spec-growth rule: "A spec must pass locally against staging before it ships" — this is the fourth finding in this repo's history that exists only because that rule wasn't actually followed for the spec in question.

## Fix

Fixed in **PR #220** (`qa-repair/deposit-comms-dryrun-locator`, squashed to `7c5ad71`,
auto-merged into `staging` 2026-09-04T11:45:19Z) by the first-pass repair tier.

`e2e/office/deposit-comms-dryrun.spec.ts:159` gains a second filter before `.last()`:

```ts
const row = page
  .locator("div")
  .filter({ hasText: fx!.quoteRef })
  .filter({ has: page.getByRole("button", { name: /Deposit received/i }) })
  .last();
```

`hasText` alone matches every ancestor div containing the ref — including `nameAndRef`'s
own text-only inner div, which `.last()` (innermost DOM match) then selected, and which
holds no action button. Adding `has: <button>` narrows the candidate set to those ancestors
containing *both* the ref text and the button; `.last()` picks the innermost of *those*,
which is the row itself. This is the `has:`-filter option the finding's `Suspected cause`
preferred over bare `.first()`, being robust to future markup nesting rather than dependent
on ordinal position.

Test: the repair ran the spec's full `test.describe.serial` block live against deployed
staging (`E2E_BASE_URL=https://staging.ops.marleymoves.co.uk --project=office`) — 1 passed.
No app code changed; the defect was only ever in the spec's own locator.

## Summary
`SchedulerView` (`components/schedule/scheduler-view.tsx:509-510`) hard-codes `slotMinTime="07:00:00"` / `slotMaxTime="20:00:00"` on the shared FullCalendar instance used by both `/schedule/surveys` and `/schedule/removals`. FullCalendar's time-grid views (`timeGridWeek`, `timeGridDay` — i.e. the "Week" and "Day" toolbar buttons) only render events whose time falls inside that slot window; an appointment starting before 07:00 or at/after 20:00 local is completely absent from those views, with no "+N more" indicator, no scroll-to-reveal, and no visual cue that anything is hidden. The appointment is correctly persisted in the database and correctly visible in the "Month" view (`dayGridMonth`, which FullCalendar does not slot-clip) — so this is a pure display-layer silent truncation, not a data bug, but it means the two views office staff use for day-to-day allocation (Week/Day) can silently omit real bookings.

## Repro
1. Admin/office login.
2. Book a survey or removal (via `/schedule/surveys` or `/schedule/removals`, or the booking dialog reached from a lead) for a start time at or after 20:00 local, or before 07:00 local — e.g. 21:30.
3. Confirm via SQL that the `appointments` row exists with the expected `starts_at`/`ends_at`.
4. On `/schedule/surveys` (or `/schedule/removals`), switch to "Week" or "Day" view and navigate to the date the appointment falls on.
5. Expected: the appointment appears somewhere on that day's column, or at minimum some visible indicator that an out-of-range event exists.
6. Actual: nothing renders for that appointment in Week/Day view — the day column simply looks empty (or only shows other, in-range appointments) between 07:00 and 20:00. Switching to "Month" view shows the appointment correctly.

## Evidence
`components/schedule/scheduler-view.tsx:480-511` — the `views` prop only overrides `dayHeaderFormat` per-view; `slotMinTime`/`slotMaxTime` are set once, globally, outside the `views` block, so they apply to every time-grid view FullCalendar renders (this is standard FullCalendar behaviour: `slotMinTime`/`slotMaxTime` only affects `timeGrid*` views, `dayGridMonth` ignores them — which is exactly why Month view showed the appointment and Week/Day did not).

`SchedulerView` is shared by both call sites (`app/(dashboard)/schedule/surveys/page.tsx`, `app/(dashboard)/schedule/removals/page.tsx`), so the gap applies to both surveys and removals, not just one appointment type.

Live-verified this run (2026-08-23) by the admin role-agent: booked a survey via the real UI where the booking dialog's default-filled time (rounds up from "now") landed at 21:30 UK local — the appointment persisted correctly (`appointments.status='scheduled'`, correct `starts_at`), rendered zero `.fc-event` nodes in Week view for that day, and rendered correctly in Month view. Cross-checked against `.fc-event` DOM count (not raw page text, which includes an RSC payload that would false-positive a text search).

## Suspected cause
`components/schedule/scheduler-view.tsx:509-510` — `slotMinTime="07:00:00"` / `slotMaxTime="20:00:00"` should either be widened to cover the realistic range of booking times (removals in particular can start earlier than 07:00 for long-distance jobs), or the calendar should surface an explicit indicator (e.g. a banner, or an "N appointments outside visible hours" affordance) when a day has an event outside the current slot window, so office staff are never silently missing a real booking in the view they use to allocate crew day-to-day.

## Verify
Seed an appointment with `starts_at` at 21:30 (or 06:00) local on a given day. On `/schedule/surveys` and `/schedule/removals`, in both "Week" and "Day" view for that date, confirm the appointment is visible (either because the slot range was widened to include it, or because an explicit "appointments outside visible hours" indicator now appears) — not silently absent.

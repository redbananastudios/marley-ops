## Summary
Staging's bank-feed cron is NOT the documented `disabled:true` no-op — `BANK_FEED_*` is live-configured in staging's env, so every trigger pulls the real Monzo→Google-Sheets export (2,285 real bank rows this run) into a QA environment. The route's own doc-comment ("No-ops cleanly (disabled:true) until the BANK_FEED_* env is present") and the audit's standing assumption are both contradicted by the deployed config.

## Repro
1. No login — cron secret auth (`Authorization: Bearer <QA_STAGING_CRON_SECRET>`).
2. `GET https://staging.ops.marleymoves.co.uk/api/cron/bank-feed`
3. Expected (documented posture): `{"ok":true,"disabled":true}`-style no-op. Actual: HTTP 200 `{"ok":true,"rowsInSheet":2285,"skippedRows":0,"upserted":0,...}` — the real sheet was fetched and scanned. A prior `cron_runs` row from 2026-08-06 shows `rowsInSheet:2078`, so this has been live for at least a month.

## Evidence
- `cron_runs` row id `ff8ba3bd-a8bb-4732-ab37-8b717e536a83`, job `bank-feed`, started 2026-09-05T00:13:13Z, status `ok`, summary `rowsInSheet:2285`, everything else 0.
- `SELECT count(*) FROM bank_transactions` → 0 before AND after (the `BANK_FEED_SINCE` floor filtered every row before upsert), so no data landed this run — the exposure is the live pull itself plus what happens the day the floor stops filtering (real bank rows would upsert into staging and generate match suggestions against QA fixtures).

## Suspected cause
Not app code — staging `app.env` has `BANK_FEED_*` (and presumably `BANK_FEED_SINCE`) set. Decision for Peter: either unset `BANK_FEED_*` on staging (restoring the documented no-op) or document that staging deliberately mirrors the live feed read-only and rely on the SINCE floor.

## Verify
`GET /api/cron/bank-feed` with the cron secret. Close when either (a) the response is the unconfigured no-op (`disabled:true`, no sheet fetch), or (b) Peter has recorded (AGENTS.md or this file) that staging's live feed pull is intentional — in which case also assert `bank_transactions` stays 0 after a trigger.

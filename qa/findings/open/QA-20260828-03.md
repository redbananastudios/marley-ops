## Summary
A commercial quote (`payment_policy` resolving to `'commercial'`) that is `status:'sent'` still renders the full residential accept flow at `/q/<token>` — an enabled "Accept quote & pay £100 deposit" button and copy promising a deposit the client does not owe — even though PRD §3.10 says a commercial quote should render for review only, with no accept action, and gate 10b's own commit message states "the button was already hidden." It was not hidden on this page. The server-side refusal in `lib/quote/accept-flow.ts` (the actual gate 10b fix) does correctly block the write if the customer clicks through anyway — this is a UI/copy bug, not a money-safety hole.

## Repro
1. No login needed (public token page).
2. Seed a `clients` row with `is_company: true`, a `leads` row for it, and a `quotes` row referencing that lead/client with `status: 'sent'`, `accept_token: '<token>'`, `agreed_price`/`grand_total` set, `payment_policy: null` (correct pre-accept shape — it is only snapshotted at acceptance).
3. Visit `https://staging.ops.marleymoves.co.uk/q/<token>`.
4. Expected: a review-only render — no accept button, no deposit figure/copy (PRD §3.10: "a commercial quote renders for review with no accept action").
5. Actual: the ordinary residential accept screen renders — headline total, "Accepting reserves your date. A £100 deposit secures the booking — pay by card or bank transfer on the next screen," and an enabled `AcceptForm` button.
6. If the customer completes the form anyway (ticks acks, submits): the server correctly refuses with "This quote is on business terms - we'll confirm it with you and invoice on your account." A SQL read-back of the quote row after that submit confirms no side effect: `status` unchanged (`'sent'`), `payment_policy` unchanged (`null`), `accepted_at: null`, `zoho_deposit_invoice_id: null` — no deposit invoice was raised. So the bug is confined to the render; nothing downstream is at risk.

## Evidence
`app/q/[token]/page.tsx`'s `quote.status === "sent"` branch (~line 246) renders `SummaryRows`, the deposit-copy block and `<AcceptForm token={token} depositLabel={gbp(deposit)} />` unconditionally — no read of `payment_policy` or the client's `is_company` anywhere in that branch, or anywhere else in the file (`grep -i "commercial\|payment_policy"` against `page.tsx` and `accept-form.tsx`: zero matches). Contrast with the write path: `acceptQuoteOnlineAction` in `lib/quote/accept-flow.ts:662` calls `snapshotPaymentPolicy(sb, quote)` — which derives the policy live from `clients.is_company` via `resolvePaymentPolicy` (same lookup, pre-accept-safe) — and refuses before any write (lines ~676-681) when the result is `'commercial'`. The page has the same `quote.client_id`/`quote.lead_id` available and could call the identical resolution before choosing which branch to render; it simply never does.

Live-verified against staging: seeded a `status:'sent'` commercial-shaped quote, fetched `/q/<token>`, confirmed the button/copy render as described; submitted the form, confirmed the correct server refusal message and a no-op SQL state; deleted all marker rows afterward (0 remaining).

## Suspected cause
`app/q/[token]/page.tsx`, the `status === "sent"` render branch (~lines 244-291) — never calls `resolvePaymentPolicy`/an equivalent live client lookup before deciding what to render, unlike the accept action in the same file's sibling module which already does this correctly. The repair agent should reuse `resolvePaymentPolicy`/`snapshotPaymentPolicy`'s lookup pattern (or export `snapshotPaymentPolicy` for reuse) rather than re-deriving it, and render a review-only card (no `AcceptForm`, no deposit copy) when the resolved policy is `'commercial'` — matching the tone of the server refusal copy already shipped in `accept-flow.ts`.

## Verify
Seed a `status:'sent'` quote whose client has `is_company:true` (no `payment_policy` column value needed — it must be resolved live, matching pre-accept reality). Visit `/q/<token>`: no accept button, no deposit copy must render; a review-only message should appear instead. A parallel residential `status:'sent'` quote (`is_company:false`) visited the same way must be completely unaffected — accept button and deposit copy still render exactly as before.

## Summary
`/clients` throws React error #418 (hydration mismatch) in the browser console on every load. The page renders correctly, but a hydration mismatch forces a client re-render of the tree and can mask genuine bugs behind the constant console noise.

## Repro
1. Role: office (staging, commit bf678a9 — but pre-existing, not gate-12 work; neither gate-4 nor gate-12 diffs touch a date-rendering path here).
2. Open `/clients` with the browser console visible.
3. Expected: no console errors.
4. Actual: minified React error #418 (text-content mismatch between server and client render) on every load, both List and Grid modes.

## Evidence
Observed live by the gate-12 role-QA agent (2026-08-26) on every `/clients` visit during its run, alongside otherwise-passing assertions. Likely cause: a relative-date or locale-formatted string computed at render time (server timezone/locale vs browser) — the usual #418 shape in this codebase's list pages.

## Suggested angle (for the repair tier)
Un-minify locally (`npm run dev`, open /clients) to get the exact mismatching text node, then anchor the offending timestamp/relative-date through a deterministic formatter or a `suppressHydrationWarning` ONLY if the value is genuinely client-local by design.

## Fix

Root cause confirmed as the suspected shape: `dateShort` in
`components/clients/clients-view.tsx` called `toLocaleDateString("en-GB", …)`
with NO `timeZone`, and the "Last enquiry" text renders in both view modes
(list table column and card footer). The server renders in UTC, the browser in
Europe/London, so any `lastLeadAt` between 23:00 and 00:00 UTC during BST
formats as different dates → text-content mismatch → React #418 and a full
client re-render. Verified in this (UTC) container: `2026-08-25T23:30:00Z`
formats un-pinned as "25 Aug 2026" vs "26 Aug 2026" pinned to Europe/London.

Change (matches the house pattern — every other list/detail formatter pins
`timeZone`, e.g. `app/(dashboard)/clients/[id]/page.tsx` uses `UK_TZ`):
- `lib/uk-time.ts`: new `ukDateShort()` — the same "26 Aug 2026" format pinned
  to `UK_TZ`; module header updated (its "client components are fine as-is"
  claim is exactly what this finding disproved for SSR'd text).
- `components/clients/clients-view.tsx`: local un-pinned `dateShort` deleted,
  replaced by `import { ukDateShort as dateShort }`. No other nondeterministic
  render text on the page (scanned all components /clients mounts; the
  compose-dialog's `toLocaleString` renders only after user interaction, not
  at hydration).

Safe because it is display-only text formatting — no data, money, or query
paths touched; visible output changes only for the boundary timestamps that
previously rendered the (wrong) UTC date, which now match the client detail
page's UK_TZ semantics.

Test: `tests/lib/uk-time.test.ts` — behavioral asserts on the BST boundary
instant (fails before on a UTC runner: "25 Aug 2026" ≠ "26 Aug 2026"), winter
GMT agreement, and placeholder handling, plus wiring asserts that the view
imports the shared helper and contains no un-pinned `toLocaleDateString`
(fails before in ANY host timezone).

Note for the audit: the same un-pinned `dateShort` copy exists in
`components/board/status-board.tsx` and `components/quotes/quotes-view.tsx`
(day+month only, no year). Out of this finding's scope (/clients), left
untouched — worth its own finding if #418 shows on /leads or /quotes.

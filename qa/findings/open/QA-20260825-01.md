## Summary
A crew sign-up applicant who types their postcode without the canonical internal space (e.g. `sp71ab`) gets it stored and displayed as `SP71AB` instead of the correctly formatted `SP7 1AB`.

## Repro
1. Public token page, no login: `https://staging.ops.marleymoves.co.uk/join/<a live staff_onboard_token>` (confirm `business_settings.staff_onboard_enabled=true` first — read-only, do not toggle it).
2. Fill the sign-up form, typing the postcode field as `sp71ab` (lowercase, no space).
3. Submit.
4. Expected: the stored/displayed postcode is normalised to standard UK format `SP7 1AB`.
5. Actual: stored and displayed as `SP71AB` — uppercased but never re-spaced.

## Evidence
`staff_submissions` row (this run's marker, since deleted): `address_postcode: "SP71AB"`, and the derived one-line `address` field built from it also reads `"...SP71AB"` — both surfaces agree with each other, so this is not a two-hats disagreement, just a missing formatting step applied consistently everywhere.

The validation regex accepts a postcode with no space at all:
```
lib/staff/onboarding.ts:46
const UK_POSTCODE_RE = /^[A-Za-z]{1,2}\d[A-Za-z\d]?\s?\d[A-Za-z]{2}$/;
```
(the `\s?` makes the internal space optional), and the transform that runs after validation only uppercases, it never re-inserts the space:
```
lib/staff/onboarding.ts:71-72
    .refine((s) => UK_POSTCODE_RE.test(s), "Enter a valid UK postcode")
    .transform((s) => s.toUpperCase().slice(0, 10)),
```

## Suspected cause
`lib/staff/onboarding.ts:71-72` — the `.transform()` needs to insert the canonical space before the last 3 characters (outward code vs inward code), not just uppercase. E.g. `s.toUpperCase().replace(/\s+/g, "").replace(/(.+)(\d[A-Z]{2})$/, "$1 $2").slice(0, 10)`.

## Verify
Submit `/join/[token]` with postcode typed as `sp71ab` (or any valid no-space postcode) and confirm the stored `staff_submissions.address_postcode` reads `SP7 1AB` (correctly spaced), not `SP71AB`.

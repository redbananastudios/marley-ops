## Summary
Every quote created for a non-default-brand (Pitmans) lead is denormalised with `quotes.brand = "pitmans"` correctly, but its `quote_ref` is always minted with the **Marley** prefix (`MMR###`/`MMC###`) instead of Pitmans' (`PMR###`/`PMC###`) — the brand chip, filter, and `brand` column are right; the customer-facing reference number (and the subject line/PDF/bank-reconciliation trail built from it) is wrong.

## Repro
1. Role: admin (staging).
2. Have (or create via `/leads/new` picking "Pitmans") a lead with `brand='pitmans'`.
3. Navigate to `/quotes/new?leadId=<that lead id>` (or click "New quote" from the lead page) — this creates a draft quote via `createDraftQuote`.
4. Expected: `quote_ref` starts with `PM` (migration 0104's own comment: "next_quote_ref can mint MMR042 and PMR001 from the same code path").
5. Actual: `quote_ref` starts with `MM`.

## Evidence
Reproduced live on staging, 2026-08-25, by two independent parties:

Role agent (browser-driven, 3x): 
- Lead `8b46b7e3-36b5-4f2e-9e1a-d6ea6587bc50` (`leads.brand='pitmans'`) → quote `2af2b85a-e0be-4121-9464-01b1825d3e28`: `{"brand":"pitmans","quote_ref":"MMR085"}`
- Lead `c37bfce6-95ab-48ce-8fd2-1e3951827159` (`leads.brand='pitmans'`) → quote `cb65f8a4-164b-44ed-bbc3-33353f11535f`: `{"brand":"pitmans","quote_ref":"MMR086"}`, and its revision quote `28c6a5fb-14e9-43d9-ae32-be4fd0bbf352`: `{"brand":"pitmans","quote_ref":"MMR087"}`
- The sent email's own subject line surfaced the mismatch: `"Your removal quote from Marley Moves — MMR086"` for a Pitmans quote.

Main-loop independent spot-check (RPC-level, not browser-driven — confirms the exact root cause, not just the symptom):
```
next_quote_ref(kind: "R")                    -> MMR088   (app's actual call shape — no brand arg)
next_quote_ref(kind: "R", brand: "pitmans")   -> PMR001   (RPC already supports this; just isn't asked)
```

## Suspected cause
`app/(dashboard)/quotes/actions.ts:44`, inside `nextQuoteRef()`:
```ts
const { data, error } = await sb.rpc("next_quote_ref", { kind });
```
never passes `brand`, so it always falls through to the RPC's `brand text default 'marley'` (migration `0104_brands.sql:214`) — even though `createDraftQuote` already resolves `lead?.brand ?? DEFAULT_BRAND` two lines below for the `brand` column write (`quotes/actions.ts:165`). The fix is passing that same resolved brand into the RPC call: `sb.rpc("next_quote_ref", { kind, brand })`.

Downstream effect: Pitmans' `brand_ref_counters` row (`kind IN ('R','C')`) is never incremented — it stays at 0 indefinitely while Marley's counter absorbs both brands' quotes — which will also eventually collide with the "PMR001 already issued to a customer, never reissue" invariant documented in `0104_brands.sql` once this is fixed naively. A correct fix must NOT reissue any `MMR###` ref already sent to a Pitmans customer under this bug — flagging as `risky` for that reason, plus its bank-reconciliation and quote-ref-immutability implications (`leads/actions.ts` documents the ref is fixed once issued specifically so it can be trusted downstream).

## Verify
Create a quote for a lead with `brand='pitmans'` (via `/quotes/new?leadId=...` or "New quote") and confirm `select brand, quote_ref from quotes where id='<new id>'` returns a `quote_ref` matching `^PM[RC]\d+$` for `brand='pitmans'` (and still `^MM[RC]\d+$` for `brand='marley'`). Also confirm no already-issued `MM`-prefixed ref belonging to a Pitmans quote gets silently reissued/changed by the fix — those rows keep their existing (wrong-prefix but already customer-facing) ref; only NEW quotes mint correctly going forward, unless Peter decides otherwise.

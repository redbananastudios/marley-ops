## Summary
The signed-contract PDF endpoint is documented "Office-only. It contains the customer's signature and IP address," but its only guard is `requireApiUser()`, which returns any authenticated user's id with **no role check**. A logged-in **crew** user — RLS-walled from every office money/customer surface elsewhere — can fetch any customer's signed contract PDF (signature image, acknowledgment wording, IP address, timestamp). The route renders through `createAdminClient()` (service role), so RLS does not backstop the missing role gate either.

## Repro
1. Mint (or use) an active **crew**-role profile — `profiles.role='crew'`, `active=true` (this run used a QA-SENTINEL crew user).
2. Pick any existing signature id via service-role SQL: `select id, kind from signatures order by signed_at desc limit 1;` (do not paste a real customer's id into committed artifacts — resolve it live).
3. Log in to https://staging.ops.marleymoves.co.uk/login as the crew user. The office UI itself correctly bounces crew: `app/(dashboard)/layout.tsx:24` redirects `role==='crew'` to `/my-jobs`. But API routes have no layout.
4. From that authenticated crew session, GET `https://staging.ops.marleymoves.co.uk/api/documents/contract/<signatureId>`.
5. Expected: 401/403 (office-only, per the route's own docstring). Actual: **200, `application/pdf`, 64,136 bytes, `%PDF-` magic** — the full signed contract, identical byte-length to the admin fetch of the same id.

## Evidence
Live proof this run (Playwright, real sessions, deployed staging `ae9edab`):
```
admin:  status=200 bytes=64136 magic="%PDF-" content-type=application/pdf
crew:   status=200 bytes=64136 magic="%PDF-" content-type=application/pdf   ← office-only doc served to crew
crew profile: {"role":"crew","active":true}   (confirmed via profiles read-back)
```
Source, read 2026-08-21:
- `app/api/documents/contract/[signatureId]/route.ts:22` — docstring: "Office-only. It contains the customer's signature and IP address."
- `app/api/documents/contract/[signatureId]/route.ts:42` — `const userId = await requireApiUser(); if (!userId) return 401;` — the ONLY guard. No role assertion.
- `app/api/documents/contract/[signatureId]/route.ts:3,45` — `createAdminClient()` (service role) reads the signature, so RLS cannot re-gate it.
- `lib/api-auth.ts:10-15` — `requireApiUser()` returns `user?.id ?? null`: authentication only, role-blind.
- Contrast, same directory: `app/api/automations/runs/route.ts:8-9` deliberately queries "through the signed-in user's client so RLS (cron_runs_read → is_office()) gates it to office/admin; crew never see the log." The contract route wanted the same office-only guarantee and did not get it.

## Suspected cause
Defense-in-depth gap: the route relies on the proxy/layout to keep crew out, but the proxy only refreshes the session and the layout gate applies to `(dashboard)` pages, not `/api/**`. `requireApiUser()` was the wrong helper for an office-only route — it authenticates but is role-blind.

A ready-made fix exists in this codebase: `lib/ai/auth.ts#requireOfficeProfile()` — "Active admin/estimator gate for every AI action and route. Crew is denied." — is exactly the guard this route needs, and is already used by the sibling admin-client route `app/api/ai-surveys/state/route.ts:10` (`if (!(await requireOfficeProfile())) return 403`). A one-line swap of `requireApiUser()` for `requireOfficeProfile()` closes the leak while keeping office access. (An audit of all non-cron API routes using the admin client this run found this is the ONLY one with a role-blind guard; `ai-surveys/state`, `card/*`, `ingest/lead` are each correctly gated.)

## Verify
1. As an active crew-role session, GET `/api/documents/contract/<any real signatureId>`.
2. Assert the response is a refusal (401/403), NOT a `%PDF-` body. Assert an admin session still gets the 200 `%PDF-` document for the same id (the fix must not break office access).

## Summary
The customer-facing cubic-survey self-fill page (`/cv/<token>`) has no photo-upload control at all — a customer can list items and write notes, but cannot attach a single photo — even though the admin's own cubic review UI for the exact same survey shows a working "Survey photos" upload widget, and the intended handoff ("customer submits `/cv` survey → admin reviews it, media playable") explicitly expects a photo to exist for the admin to review.

## Repro
1. No login needed. Seed (or use) a `cubic_surveys` row with a `share_token`, e.g. via the service-role client:
   ```js
   await sb.from('cubic_surveys').insert({ lead_id, client_id, share_token: '<token>', status: 'draft' });
   ```
2. Visit `https://staging.ops.marleymoves.co.uk/cv/<token>` as a customer would.
3. Add at least one item, scroll to the bottom of the page.
4. Expected: some affordance to attach a photo of the item(s) — a file input, camera capture, or drag-drop target — matching the "Survey photos" widget office staff see on the equivalent admin review page for the same survey.
5. Actual: only a customer-notes textarea appears. A full HTML dump of the `/cv/<token>` page contains zero `<input type="file">` elements and zero references to the `SurveyPhotos` component anywhere in the DOM.

## Evidence
`components/cubic/cubic-builder.tsx` line 741 renders `<SurveyPhotos>` only when `office && leadId` is true:
```tsx
{office && leadId ? (
  <SurveyPhotos ... />
) : null}
```
`app/cv/[token]/page.tsx` invokes `<CubicBuilder mode="customer" .../>` and never passes a `leadId` prop, so `office` is false and `leadId` is undefined for every customer-mode render — the photo widget can never mount on this route, regardless of the survey's actual state. Confirmed live: fetched the full rendered HTML of a real `/cv/<token>` page (marker survey, share_token `qa-sentinel-cv-jxi197`) and grepped it — 0 matches for `type="file"` or `SurveyPhotos`. The admin review page for the same survey (`/leads/<id>/cubic`) does render the widget (screenshot confirms an empty "Survey photos" upload area present).

## Suspected cause
`components/cubic/cubic-builder.tsx:741` (the `office && leadId` gate) — `app/cv/[token]/page.tsx` never supplies `leadId` in customer mode, so the gate is unconditionally false on this route. The underlying photo-storage pipeline (bucket + `job_media`/survey-photo table) already works for office mode and looks reusable for customer mode; the repair agent should verify independently which prop/condition is the actual blocker before changing the gate.

## Verify
On `/cv/<token>` for a fresh marker cubic survey (no `leadId` involved), a photo-upload control must be present and usable: the customer can select/capture a file, it uploads, and afterward a service-role read-back of the survey's photo-storage table shows a row whose referenced storage object actually exists in the bucket (non-zero bytes). The admin review page for the same survey must then show that same photo as loadable (non-zero bytes, correct content-type), not just a stored path.

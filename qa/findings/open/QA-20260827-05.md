## Summary
When a "Moving from"/"Moving to" postcode is typed by hand (no Places-autocomplete pick), `leads.from_postcode`/`to_postcode` are correctly normalised (e.g. `"BH21 8NB"`) but the sibling `leads.from_address`/`to_address` columns store the raw, un-normalised text as typed (e.g. `"bh218nb"`) — the lead detail page then shows a normalised "Route" line right next to a raw-text "Pickup/Destination address" line for the same logical value.

## Repro
1. Role + login: admin (office), marker admin login.
2. On `/leads/new`, fill the required fields (brand, name, phone/email, source), then in the "Moving from" address block leave Street/Town/County blank and type a lower-case/no-space postcode directly into the Postcode field without picking a Places autocomplete suggestion (e.g. `bh218nb`). Repeat for "Moving to" (e.g. `sp78ab`). Submit.
3. Expected: `from_address`/`to_address` reflect the same normalised postcode as `from_postcode`/`to_postcode` (both derived from the one value the user typed).
4. Actual: `from_postcode`/`to_postcode` are normalised (`"BH21 8NB"`/`"SP7 8AB"`) via the server-side `formatUkPostcode` transform, but `from_address`/`to_address` are built client-side by `formatAddress()` from the raw, un-transformed address-fields state and stored verbatim (`"bh218nb"`/`"sp78ab"`). The lead detail page renders `Route: "BH21 8NB → SP7 8AB"` (correct) directly beside `Pickup address: "bh218nb"` / `Destination address: "sp78ab"` (raw) — inconsistent display of the same underlying value on one screen.

## Evidence
Live run (2026-08-27, run `a2c1503`), lead id `fa499051-c4af-4baf-912f-9c71b8038b2f`:
```
select from_postcode, to_postcode, from_address, to_address from leads where id = 'fa499051-c4af-4baf-912f-9c71b8038b2f';
-- from_postcode: "BH21 8NB"   to_postcode: "SP7 8AB"
-- from_address:  "bh218nb"    to_address:  "sp78ab"
```
The lead has since been deleted as a QA-SENTINEL marker row (part of this run's cleanup) — reproduce fresh with a new marker lead per the repro steps above.

## Suspected cause
`app/(dashboard)/leads/new/add-lead-form.tsx` `onSubmit` (~line 200-208): `from_address: formatAddress(fromAddr)` (and the `to_address` sibling) build the address string from the raw `fromAddr`/`toAddr` state, whose `postcode` field is never passed through `formatUkPostcode` before being joined — unlike `from_postcode`/`to_postcode`, which the server-side insert normalises separately. `components/places/address-fields.tsx`'s `formatAddress()` applies no normalisation itself. The same pattern likely also applies to the lead edit path (`components/leads/edit-lead-dialog.tsx`), not separately verified this run — the repair agent should check both call sites.

## Verify
1. Seed (or drive via UI) a marker lead with a hand-typed, un-normalised postcode in both address blocks and no Places-autocomplete pick.
2. Query `leads.from_postcode`, `to_postcode`, `from_address`, `to_address` for that row.
3. Pass: `from_address`/`to_address` contain the same normalised postcode text as `from_postcode`/`to_postcode` (not the raw as-typed text). Fail: they still diverge.

## Resolution (2026-08-28, branch `qa/ui-safe-fixes`)

Confirmed still real for `/leads/new`. **NOT real for the lead-edit path**,
which this finding flagged as unverified: `edit-lead-dialog.tsx` does not use
`formatAddress` at all - its own `streetPart()` joins line1/town/county and
deliberately excludes the postcode, so no postcode is ever embedded on edit.

**Fixed** in the shared joiner `formatAddress` rather than at the call site.
Its own file header calls it the single joiner used everywhere so addresses
stay conformant, it is currently the only caller, and fixing it there protects
any future one. It now runs the postcode through `formatUkPostcode`, the same
canonical helper the server applies to the sibling column.

Deliberately reusing that helper rather than hand-rolling a second normaliser -
the review of an earlier robot fix (#82) criticised exactly that.

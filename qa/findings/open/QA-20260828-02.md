## Summary
`app/(dashboard)/quotes/new/page.tsx` performs a database **write during its Server Component render** and then `redirect()`s. Next can invoke that render twice for one client-side navigation, and while the resulting DB race is handled, the two `redirect()` throws are not — which is what showed the generic error boundary in QA-20260827-03. That finding was fixed at the one call site it reproduced against (`appointment-view-dialog.tsx`, which used a bare `router.push`). **Seven other call sites reach the same page through `<Link prefetch={false}>` and share the same hazard**, because the fault is in the page render, not in how the navigation was started.

## Repro
1. Role: admin or estimator (staging).
2. Precondition: a lead that has never had a quote.
3. From any of the seven entry points below, click the "New quote" link — a client-side transition, not a hard load:
   - `app/(dashboard)/leads/[id]/page.tsx:724`
   - `components/board/status-board.tsx:600`
   - `components/leads/lead-action-bar.tsx:210` and `:223`
   - `components/leads/leads-board.tsx:637` and `:829`
   - `components/leads/mark-won-button.tsx:215`
4. Expected: lands in the quote builder at `/quotes/{new draft id}`.
5. Actual: intermittently renders the generic error boundary, while the draft quote IS created. A hard reload of the identical URL always works.

Intermittent by nature — it depends on Next invoking the render twice for that navigation, which is not deterministic. That is precisely why it needs fixing structurally rather than being chased as flake.

## Evidence
The codebase already documents the double-invocation, in `app/(dashboard)/quotes/actions.ts:213-215`:

> `/quotes/new` creates the draft during its render, which Next can fire twice for one navigation, and both passes clear the resume check above before either commits.

The DB consequence is handled there (partial unique index `quotes_one_draft_per_lead_uq` + re-read-the-winner, so both passes return `{ok:true}`). Nothing handles the two `redirect()` throws.

Corroborating: `e2e/estimator/work-quote.spec.ts:150-159` wraps the `<Link>` click at exactly this entry point in a **3-attempt retry loop with no comment explaining why**, which reads as a prior workaround for this same crash rather than ordinary flake-proofing. That spec is currently skipped in CI for a missing `E2E_ESTIMATOR_PASSWORD`, so it provides no cover either way.

## Suspected cause
A write performed during render is not idempotent with respect to Next's render invocations. The fix is to stop writing during the render: make `/quotes/new?leadId=` either read-only (render a builder that creates the draft on first save) or have every entry point call `createDraftQuote` as a server action and navigate to `/quotes/{id}` directly — which is what QA-20260827-03's fix did for the one call site it covered.

Deliberately NOT folded into that fix: it changes seven entry points plus three e2e specs that `page.goto('/quotes/new?leadId=…')` and rely on the redirect, so it needs its own change with its own verification rather than riding along in a minimal safe-fix.

## Verify
For each of the seven entry points, click through on a lead with no prior quote and assert `/quotes/<uuid>` with no error boundary, and exactly one `quotes` row for that lead. Then remove the unexplained retry loop in `e2e/estimator/work-quote.spec.ts` and require success on the first attempt — as written it would mask exactly this bug.

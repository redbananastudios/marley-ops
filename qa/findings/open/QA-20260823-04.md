## Summary
The crew push-notification opt-in panel on `/my-jobs` still promises "you're
put on a job — or taken off one" alerts, but that push category was retired
today — a crew member who enables notifications believing this will get zero
job-assignment pushes, silently.

## Repro
1. Any crew login → `/my-jobs` → expand "Get job alerts on this phone"
   (the `NotificationsRow` panel above `NotificationsSetup`).
2. Read the panel copy.
3. Expected: copy describes what push notifications actually do today.
   Actual: `components/my-jobs/notifications-row.tsx:25` reads *"Get a
   notification when you're put on a job — or taken off one — even when
   this app is closed."*

## Evidence
`git show bd58fa0` (`feat(crew): retire realtime crew-allocation pushes;
the job sheet is the channel (#56)`, landed 2026-08-23T15:37 UTC — the same
day, ahead of this audit run) deliberately removed the `crew_job` push
category entirely: `lib/push/categories.ts` no longer defines it
(`tests/lib/push/categories.test.ts` asserts
`"crew_job" in PUSH_CATEGORIES === false`), the Job Board fire points were
deleted, and `lib/push/crew.ts` was removed outright. That commit updated
`components/push/notifications-setup.tsx` (dropped the admin's "Crew job
assignments" toggle) but did **not** touch
`components/my-jobs/notifications-row.tsx`, whose copy is the only
crew-facing surface still describing the retired feature. Grep for
`crew_job` under `lib/push/`, `app/actions/push.ts`, and `components/`
returns zero hits — only the now-dead, unread
`business_settings.push_crew_job_enabled` column survives (left in place
per bd58fa0's own commit message).

Live-confirmed on staging (301912b): `business_settings.push_enabled=false`
(the master kill switch, unrelated to this bug), `push_subscriptions`/
`push_preferences` both 0 rows. A crew login's `/my-jobs` panel still
renders the stale copy above `NotificationsSetup` regardless.

## Suspected cause
`components/my-jobs/notifications-row.tsx:24-27` — static paragraph never
updated when `bd58fa0` retired the `crew_job` push category.

## Verify
Load `/my-jobs` as any crew login, expand the notifications panel, and
confirm the copy no longer promises job-assignment push alerts (it should
describe whatever the current value proposition is, e.g. pointing crew at
the job sheet, or be removed/genericised if there is nothing left worth
promising).

## Fix (pending live verification)
The copy was the visible half. The whole panel is inert for its only audience:
`bd58fa0` left every remaining push category office-only (`admin`/`estimator`),
and `getPushConfigAction` filters categories by role — so a crew member who taps
"Enable notifications" spends the browser's one-shot permission prompt, gets an
empty "What you receive" list, and receives nothing, forever, silently. A denied
prompt is close to unrecoverable, so offering it is pure downside.

- `lib/push/categories.ts` — new `pushCategoriesForRole(role)`, the single source
  of truth for both the preference list and whether to offer the opt-in at all.
- `app/actions/push.ts` — uses it (the audience filter was duplicated inline) and
  drops the stale "crew see job assignments" comment.
- `components/my-jobs/notifications-row.tsx` — renders `null` when the viewer's
  role receives nothing, and no longer carries its own hardcoded promise;
  `NotificationsSetup` already states the accurate copy for every state. Gating on
  the registry rather than on `role !== "crew"` means the row returns by itself
  the day a crew-audience category is added.
- `tests/lib/push/categories.test.ts` — 3 tests. Mutation-verified: adding `crew`
  to any audience fails the guard.

## Summary
The permanent CI spec for handoff h8 (`e2e/office/removal-changedate-to-crew.spec.ts`) creates real `communications` and `activities` rows as a side effect of the flow it tests (the "your move date has changed" email + a note logged against the lead), but its `test.afterAll` teardown never deletes either table. Because `communications.lead_id` and `activities.lead_id` carry `ON DELETE RESTRICT`-style foreign keys back to `leads`, the teardown's `leads` delete then fails with a Postgres `23503` foreign-key-violation on every single CI run, which cascades to also leave the `clients` row behind (its delete is guarded by the same failed lookup). The failure is silent — none of the teardown's `await sb.from(...).delete(...)` calls check the returned `error`. Net effect: every CI run of this spec permanently leaves a full `QA-SENTINEL h8 spec` client+lead+communications+activities set in the **staging** database, forever, with no bound on growth.

## Repro
1. No login needed — this is a pure DB read/write repro, not a UI repro.
2. Run the spec in CI (or `npx playwright test e2e/office/removal-changedate-to-crew.spec.ts` against staging) start to finish once. It passes green.
3. Query staging directly with the service key:
   ```js
   const { data } = await supabase.from('leads').select('*').ilike('notes', '%QA-SENTINEL h8 spec%');
   ```
   Expected (if teardown worked): `0` rows. Actual: 1 new row per run, accumulating indefinitely — this run found **4 leftover full sets** (leads/clients/communications/activities) from CI runs at `2026-08-23T16:44Z`, `16:55Z`, `18:44Z`, and `19:04Z`, none cleaned up.
4. Directly attempting the teardown's own final step reproduces the exact failure:
   ```js
   const { error } = await supabase.from('leads').delete().eq('id', '<one of the leftover lead ids>');
   ```
   Actual: `error.code === '23503'`, `error.message === 'update or delete on table "leads" violates foreign key constraint "communications_lead_id_fkey" on table "communications"'`, `error.details === 'Key (id)=(<id>) is still referenced from table "communications"'`.

## Evidence
`e2e/office/removal-changedate-to-crew.spec.ts:176-189` (`test.afterAll`):
```ts
test.afterAll(async () => {
  if (!dbReady || !leadId) return;
  const sb = db();
  const { data: appts } = await sb.from("appointments").select("id").eq("lead_id", leadId);
  const apptIds = (appts ?? []).map((a) => a.id);
  if (apptIds.length) {
    await sb.from("appointment_assignments").delete().in("appointment_id", apptIds);
    await sb.from("appointments").delete().in("id", apptIds);
  }
  await sb.from("quotes").delete().eq("lead_id", leadId);
  const { data: lead } = await sb.from("leads").select("client_id").eq("id", leadId).single();
  await sb.from("leads").delete().eq("id", leadId);
  if (lead?.client_id) await sb.from("clients").delete().eq("id", lead.client_id);
});
```
No call to `.from("communications")` or `.from("activities")` anywhere in the file. The spec's own test body (`test("admin: change the move date inside the 7-day window", ...)`) drives the real "Release old date … rebook" action, which server-side sends the "Your move date has changed" email (logged into `communications`) and writes a `note` activity into `activities` — both scoped to `leadId`/`client_id`. Confirmed live against staging 2026-08-23T20:07Z:
- `activities` leftover rows (this run found 8 across the 4 leftover sets — 4× `email_sent`, 4× `note`), each `lead_id` matching one of the leftover leads.
- `communications` leftover rows (4, one per run), each `lead_id` matching one of the leftover leads, `status='sent'`, `provider_id` starting `dryrun-email-...` (dry-run confirmed, not a real send).
- Deleting `activities` and `communications` scoped to those `lead_id`s FIRST, then `leads`, then `clients`, succeeds cleanly and re-verifies at 0/0/0/0 — proving this is the complete and sufficient fix (this run performed exactly that cleanup by hand as part of its leftover sweep).

## Suspected cause
`e2e/office/removal-changedate-to-crew.spec.ts:176-189` — the `afterAll` teardown was written to mirror only the tables the `beforeAll` seed touches directly (`clients`/`leads`/`quotes`/`appointments`/`appointment_assignments`), missing the two tables the tested ACTION itself writes into (`communications`, `activities`) as a side effect of sending the crew notification. None of the delete calls check their `error`, so the FK violation on the `leads` delete is swallowed instead of failing the test run.

## Verify
Run the spec once against staging, then query `communications` and `activities` filtered to `lead_id` values matching any lead whose `notes ilike '%QA-SENTINEL h8 spec%'` — expect 0 rows in both after the run completes (not just `leads`/`clients`/`quotes`/`appointments` at 0, which already pass today). A `leads`/`clients` count of 0 immediately after a run, with no manual intervention, is the full regression guard.

## Fix (pending live verification)
`test.afterAll` now deletes the children the tested flow actually creates — the
"your move date has changed" `communications` row and the `activities` note —
plus `surveys`/`follow_ups` defensively, **before** `leads`. More importantly it
stops being silent: every delete's `error` is collected, the lead is **read back**
to prove it is gone (a delete that removed nothing returns no error either), and
anything left throws. The thrown message carries Postgres's own constraint name,
so the next table to appear here names itself instead of costing this diagnosis
again.

A red pipeline is the correct outcome for a teardown that cannot finish: the
alternative is what happened here — unbounded silent growth in the staging DB
behind a green tick.

Also purged the leaked set still present in staging (one lead/client set from the
08:52Z CI run; the earlier occurrences had already been swept by the 20:07Z audit,
which is why this found 1 rather than the 4 the finding recorded). Read-back
verified 0 remaining.

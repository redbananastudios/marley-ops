## Summary
The handoff spec's "customer landed on the pay screen" sentinel is `getByText(/Pay by bank transfer/i)`. Since PR #181, staging's SENT-state `/q` page renders "pay by **bank transfer on the next screen**, or call us…" whenever `cardOk` is false — and staging's global `business_settings.card_payments_enabled` is `false`, so it always is. The sentinel therefore matches the PRE-accept screen the instant the accept button is clicked, the spec's very next step reads the quote row from the DB while `acceptQuoteOnline` is still in flight, and the assert sees `status: "sent"`. The spec then fails, its teardown runs while the action is still inserting rows, and the FK-ordered deletes (`activities` before the action's late `activities` insert, then `leads`, then `clients`) leave an orphaned client+lead+activities set behind on every failure. This spec has failed every real CI run since `076e46f` (#181, 2026-09-01T14:48Z) and is one of the two causes behind the QA-20260901-02 red-CI streak. The app is NOT broken — see Evidence.

## Repro
1. No login (the spec's customer leg is anonymous). Staging deployed sha `82dac7a`, `business_settings.card_payments_enabled = false` (verified by service-role read 2026-09-02).
2. CI run 33550139166, job `e2e` (id 99998500757): `customer-accept-to-bookings.spec.ts:135` fails `expect(data?.status).toBe("accepted")` with `"sent"`, then `teardown left rows behind: leads … activities_lead_id_fkey …; clients: 1 marker row(s) still present`.
3. The spec (unlike `e2e/public/customer.spec.ts`, which is correct) clicks the accept button ONCE with no `submitUntil` hydration guard and uses `/Pay by bank transfer/i` as its landed-on-pay-screen signal. `customer.spec.ts` waits for `/deposit to secure your date/i`, which only the POST-accept screen renders — that spec's UI legs pass on the same runs.

## Evidence
Service-role read-backs on deployed staging (2026-09-02, read-only):
- `business_settings.card_payments_enabled = false` → `cardOk` is false for every quote on staging → #181's card-off sentence ("pay by bank transfer on the next screen") renders on every SENT `/q` page and matches `/Pay by bank transfer/i`.
- The accepts the spec reported as "not persisted" all completed: the CI suite's own seeded quotes `E2E-SENT-001` and `E2E-LATE-001` read back `status: "accepted"` with `accepted_at` stamps from the 82dac7a run (19:45:56Z / 19:46:03Z) — on the exact deployed code the finding said could not persist an acceptance.
- The orphan sweep this run deleted 5 `E2E-H3-HANDOFF-*` client+lead sets left by the 5 failed runs of this spec, and with them **4 contract `signatures` and 2 deposit `follow_ups`** — rows only `acceptQuoteOnline` writes, AFTER the status flip. The accept ran to completion on those runs; the spec simply read the DB before it landed and then tore down underneath it. (Sweep verified: 0 rows remaining across clients/leads/activities/quotes/follow_ups/signatures.)
- First failure = `076e46f` (#181), the exact commit that introduced the card-off copy; the run before it (`710a832`) was green. #181 changed no accept logic — only the sentence that now satisfies the sentinel early.

## Suspected cause
`e2e/office/customer-accept-to-bookings.spec.ts` — three defects, all in the spec:
1. Sentinel: replace `/Pay by bank transfer/i` with the post-accept-only `/deposit to secure your date/i` (the signal `customer.spec.ts` already uses), or additionally assert the accept button is GONE.
2. Hydration/race: use the existing `submitUntil` helper (as `customer.spec.ts` does) instead of a single un-guarded click, and only read the DB after the post-accept screen is confirmed.
3. Teardown: it deletes `activities` by `lead_id` then immediately `leads`/`clients`; an accept action still in flight re-inserts `activities`/`signatures`/`follow_ups` after the delete pass. Re-running the child-table deletes once more before `leads`, or asserting the post-accept UI before teardown can start, removes the FK failure mode.

## Verify
`customer-accept-to-bookings.spec.ts` passes in a real CI e2e run against deployed staging with `business_settings.card_payments_enabled = false`, and its teardown leaves 0 rows (`clients/leads/activities` ilike `%E2E-H3-HANDOFF%` all 0 by service-role count immediately after the run).

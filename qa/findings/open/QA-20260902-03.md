## Summary
A job the crew's own job LIST already shows as "Done" (green pill, `appointments.status = 'completed'`) still shows a live "Complete job" button and no completed banner on that same job's DETAIL page, because the detail page decides "is this job completed" from a completely different source (whether a `job_completions` row exists) than the list does (`appointments.status`). A job auto-completed by the balance-settled cron — with no crew signature at all — is the case that actually falls through the gap live on staging.

## Repro
1. As crew (marker user), have a removal appointment whose `appointments.status = 'completed'` but with NO row in `job_completions` for it. This is not a contrived state: it is exactly what `app/api/cron/chase/route.ts` produces when a move's balance settles without ever creating a quote/invoice-driven crew sign-off — the cron writes `appointments.status = 'completed'` directly and logs an `activities` row `{"type":"status_change","summary":"Move day done and fully paid — auto-completed","meta":{"auto":true}}`. This happened live during this run's test, independent of the seeded fixture's intended shape, confirming the path is real.
2. Load `/my-jobs` as that crew member. The job renders with the "Done" pill (green, `lib/my-jobs/job-card.ts`'s `jobCardLook`, keyed on `status === "completed"`).
3. Open that same job's `/my-jobs/<id>` detail page.
4. Expected: a job the list already marks "Done" should read as completed on its own detail page too — no invitation to sign it off again.
5. Actual: no "Job completed" banner renders, and the pinned "Complete job" action-bar button is still live, inviting the crew to complete a job the office has already closed out.

## Evidence
Live fixture: appointment id `2860966f-71f8-42ea-b643-5e60a898712b`, `appointments.status = 'completed'` (confirmed by direct query), `job_completions` has 0 rows for `appointment_id = '2860966f-...'` (confirmed by direct query — the auto-complete cron path never inserts one, only the crew's own "Complete job" flow does).

Rendered body of `/my-jobs/2860966f-71f8-42ea-b643-5e60a898712b` for that job: "Complete Job" button count = **1**, "Job completed" banner text count = **0** — while `/my-jobs` list for the same crew member renders that job under the green "Done" pill.

Corroborating activity row written by staging's own chase cron mid-run: `{"type":"status_change","summary":"Move day done and fully paid — auto-completed","meta":{"auto":true,"appointment_id":"2860966f-..."}}`.

## Suspected cause
- `lib/my-jobs/job-card.ts` (`jobCardLook`, ~line 23): the list's "Done" pill/greyed styling is keyed purely on `status === "completed"` — this side is correct and is the source of truth the fix should follow.
- `app/my-jobs/[id]/page.tsx`: the "Job completed" banner (line 181, `{completion ? ... : null}`) and the pinned "Complete job" button (line 426, `{isRemoval && !completion ? ... : null}`) both gate purely on whether a `job_completions` row exists (`completion`, fetched lines 102-106) — they never consult `appointments.status`, so an auto-completed appointment with no `job_completions` row looks identical to a genuinely untouched one on this page.
- Fix should make the detail page treat `appointments.status === 'completed'` as completed even without a `job_completions` row (e.g. render a neutral "This job is marked complete" state and hide the "Complete job" button in that case), matching what the list already shows — without touching the auto-complete cron logic itself, which is out of scope and working as designed.

## Verify
Seed (or reuse) an appointment with `appointments.status = 'completed'` and zero `job_completions` rows for it. On `/my-jobs/<id>` for that appointment:
1. The pinned "Complete job" button must not be offered (a crew member should not be invited to sign off a job the office already closed).
2. Some visible indication that the job is complete must render (need not be the exact same "signed by..." banner used for a crew-signed completion, since there's no signer/exceptions data to show — a distinct neutral "already marked complete" state is acceptable).
3. `/my-jobs` list view for the same job must continue to show unchanged ("Done" pill, unaffected by this fix).

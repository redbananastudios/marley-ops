## Summary
One "Create Quote" click from an appointment's view dialog created **two** draft quotes 170ms apart (`MMR014` and `MMR015`, both against the same lead) instead of one — burning two sequential quote-reference numbers and leaving one orphan draft the estimator never sees, because the duplicate-draft guard in `createDraftQuote` is a plain SELECT-then-INSERT with no database constraint behind it, and `/quotes/new` performs that write unconditionally during a Server Component's render rather than behind a POST-only action.

## Repro
1. Estimator login (marker user `qa-sentinel-estimator@marleymoves.test`) on staging, 2026-08-20.
2. Lead `ec415071-1b16-469c-8976-baec0c4ea687` (QA-SENTINEL Lead) has a survey appointment. Open its view dialog, click **Create Quote**, choose "start a new quote" at the "already has quote …" prompt (`components/schedule/appointment-view-dialog.tsx:188` `onQuote()`, which does `onOpenChange(false); router.push('/quotes/new?leadId=' + lead.id)`).
3. Expected: one new draft quote, one quote-ref consumed, one navigation to `/quotes/[id]`.
4. Actual: two `quotes` rows were created, both `status=draft`, both `lead_id` = the same lead, timestamps 170ms apart:
   - `82c2ecec-305a-46ba-8459-60045b6b9a16` — `quote_ref MMR014` — `created_at 2026-08-20T04:24:25.018548+00:00`
   - `504c7448-d3c1-449b-9e63-28f269603a28` — `quote_ref MMR015` — `created_at 2026-08-20T04:24:25.188148+00:00`
   The user only ever lands on one of the two (whichever `redirect()` — see below — actually completed the navigation); the other is an invisible orphan sitting in `/quotes` with a burned, gap-making reference number.

## Evidence

```
where lead_id = 'ec415071-1b16-469c-8976-baec0c4ea687' order by created_at;

```

```
82c2ecec…  MMR014          draft     2026-08-20T04:24:25.018Z
504c7448…  MMR015          draft     2026-08-20T04:24:25.188Z
```

No unique index exists to prevent this: `grep -rn "create unique index" supabase/migrations/*.sql | grep -i quote` returns only `quotes_accept_token_uq`, `signatures_contract_uq`, `card_payments_one_pending_per_quote` — nothing scoped to `(lead_id) where status='draft'`.

## Suspected cause
`app/(dashboard)/quotes/actions.ts#createDraftQuote` (line ~80-90) reads:
```ts
// Resume an existing open DRAFT for this lead rather than piling up orphan drafts
// each time "Quote without survey" / "New quote" is opened (Peter, 2026-08-02:
// "we end up with multiple drafts")…
if (opts.leadId) {
  const { data: existingDraft } = await sb.from("quotes").select("id, quote_ref")
    .eq("lead_id", opts.leadId).eq("status", "draft")
    .order("created_at", { ascending: false }).limit(1).maybeSingle();
  if (existingDraft) return { ok: true, id: existingDraft.id, quoteRef: existingDraft.quote_ref };
}
… // falls through to INSERT a new draft
```
This is a SELECT-then-INSERT race with nothing atomic backing it — the comment shows this exact "piling up orphan drafts" symptom was already known and this check was the fix, but it only closes the race when the two calls are sequential, not concurrent. `app/(dashboard)/quotes/new/page.tsx` calls `createDraftQuote({ leadId })` unconditionally in the page's Server Component body (not inside a `"use server"` POST action gated by a button's single click) — `export const dynamic = "force-dynamic"` on a route that mutates on GET-equivalent render is exactly the shape Next.js can invoke twice for one logical navigation (link prefetch, a second RSC fetch, back-forward cache revalidation, etc.), and each invocation passes the stale-read check because neither has committed yet when the other reads.

## Suggested fix (repair agent)
Close the race at the database layer rather than the application layer: a partial unique index `create unique index quotes_one_draft_per_lead_uq on quotes(lead_id) where status = 'draft'`, then have `createDraftQuote`'s insert catch the resulting unique-violation and re-select the winning row (same pattern already used a few lines below for the `quote_ref` allocator's own duplicate/unique catch — see the `!error.message.includes("duplicate") && !error.message.includes("unique")` branch just after this function). That makes concurrent calls safe regardless of how many times `/quotes/new`'s render fires, without needing to relocate the mutation out of the page component. Add a regression test that fires `createDraftQuote({leadId})` twice concurrently (`Promise.all`) against a seeded lead and asserts exactly one draft row exists afterward.

## Verify
Seed a lead with a survey appointment, fire two concurrent `createDraftQuote({ leadId })` calls (or two rapid clicks/navigations to `/quotes/new?leadId=…`), and confirm exactly one `draft` quote row exists for that lead afterward — no orphan, no burned second quote-ref.

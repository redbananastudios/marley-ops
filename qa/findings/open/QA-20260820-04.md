## Summary
A job moving TODAY with an unpaid £1,700 balance shows up in "Owed right now" as only its £100 deposit, because `classifyBooking` is single-bucket and the deposit gate comes first — on staging, three such jobs make "Owed right now" read **£600** while the same page's Upcoming tab counts the same jobs as **£5,100 expected this week**, and /bookings "Balance outstanding" reads **£0**.

## Repro
1. State (staging seed, but reachable in prod via a hand-booked diary entry before the deposit is paid): three E2E-CREW jobs, accepted quotes £1,800 each, deposit £100 unpaid, removal appointment TODAY (2026-08-20T09:00Z), balance unpaid.
2. Admin → /payments → Due tab: "Owed right now £600.00" (6 deposits × £100, including these three); "Balance to collect 0 / £0".
3. Same page → Upcoming tab: week 17–23 Aug shows the same three jobs as 3 × £1,700 = £5,100 due 20 Aug.
4. /bookings: "Balance outstanding £0".
So the money the business is owed *today* (3 × £1,800 jobs happening today, £5,400 total unpaid) is presented as £600 owed now, £0 balance outstanding.

## Evidence
- `lib/bookings/queue.ts:61` — `if (!s.depositPaidAt) return "deposit_outstanding";` — first gate; a booking can occupy exactly one bucket, so an unpaid deposit hides the balance state entirely, including on move day.
- `app/(dashboard)/bookings/page.tsx:155-157` — `balanceOutstanding = rows.filter((r) => r.depositPaidAt && !r.balancePaidAt)…` — requires `depositPaidAt`, so a deposit-unpaid move-day job contributes £0 here.
- Service-role SQL 2026-08-20 (run artifacts `recompute-out.json`): all rendered numbers match these definitions exactly — the render is faithful; the definitions disagree with each other across tabs.

## Suspected cause
`classifyBooking`'s single-bucket ladder models the normal payment sequence (deposit → commitment → balance) and assumes the deposit is settled long before move day. A move-day booking with no deposit paid breaks the assumption: its true exposure is deposit + balance, but the ladder reports only the first unpaid rung. The Upcoming tab computes from appointments + balance independently, which is why it disagrees.

## Why risky
This is money-math classification feeding "Owed right now" — changing bucket semantics changes what the office chases and when. Options (Peter's call): let move-day (or ≤BALANCE_WINDOW_DAYS) bookings surface both amounts; or add the unpaid balance of deposit-unpaid jobs inside the due-window to "Owed right now"; or accept the current reading and document it.

## Verify
Re-create one accepted quote with unpaid deposit + removal appointment today + unpaid balance; assert "Owed right now" / "Balance outstanding" reflect whatever definition Peter chooses (and that the three surfaces — Due, Upcoming, /bookings — can no longer disagree about the same job's same-week money).

## Fix (2026-08-20, Peter's decision, applied directly — risky class, human-fixed)
Peter: "we need to see what is owed right now, so if we have a job due within the
7 day window then 25% is due - we cannot count the £100 deposits as they are not
due. only the 25% and the balance are valid."

New pure `owedNow()` in `lib/bookings/queue.ts` computes money per OBLIGATION
rather than per bucket, so an unpaid deposit can no longer mask a balance.
Deposits are excluded entirely; `BALANCE_WINDOW_DAYS` 3 → 7 to match the T-7
automatic balance invoice. The result is attached to each row once in
`load-signals.ts`, so /payments, /bookings and the dashboard tiles read one
figure. `/bookings` "Balance outstanding" no longer requires `depositPaidAt`.
No double-count: `balanceAmount` is already agreed − deposit − commitment.
8 unit tests added. Live prod effect: −£100 deposit from the headline;
£655 unpaid 25% and £2,582.30 balance due within 7 days now visible.

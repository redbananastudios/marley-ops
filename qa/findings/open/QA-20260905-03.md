## Summary
The permanent spec `e2e/office/join-approve-handoff.spec.ts` has a queue-empty assertion that isn't scoped to its own applicant's card — it counts every "Approve" button on `/resources`, so the test fails whenever any OTHER submission is still pending. That other-pending-submission state is not an edge case: it is the standing, by-design state left behind by `e2e/public/join.spec.ts`'s own fixture ("E2E Join Applicant", deliberately left `pending` until the next `e2e:seed` reseed — see that spec's own doc-comment). Since `E2E_OFFICE_PASSWORD` is a real CI secret (`.github/workflows/staging.yml:149`), this spec is NOT skipped in CI — it is a live, currently-fragile assertion whose pass/fail depends on test/worker execution order between the `public` and `office` Playwright projects in the same run, rather than on the behaviour under test.

## Repro
1. Confirm the standing fixture row exists (any environment after `e2e:seed` + a run of `public/join.spec.ts`, or currently on staging right now):
   `select full_name, status, created_at from staff_submissions where status='pending';` → returns `{"full_name":"E2E Join Applicant","status":"pending","created_at":"2026-09-05T04:43:29.251352+00:00"}` (verified live on staging by the main loop, independent of the role-agent's own run).
2. With that row present, drive `e2e/office/join-approve-handoff.spec.ts`'s own fixture through its first two tests (submit a marker application via `/join/<token>`, then approve it as admin).
3. Its third test reloads `/resources` and asserts `expect(adminPage.getByRole("button", { name: "Approve", exact: true })).toHaveCount(0)` (line 114).
4. Expected: 0 (the spec's own applicant is approved, so its card should be gone). Actual: 1 — the standing "E2E Join Applicant" card's own Approve button is still on the page and satisfies the exact same locator, since the assertion isn't scoped to the spec's own `APPLICANT_NAME` card.

## Evidence
Live run against staging this session (Sonnet customer-role agent, later independently corroborated by the main loop's own read of the same pending row): `npx playwright test --project=setup --project=office e2e/office/join-approve-handoff.spec.ts` against `https://staging.ops.marleymoves.co.uk` — 1 of 3 tests in the file failed, exactly at the line-114 assertion, "Expected 0, Received 1". The spec's own `afterAll` still tore down its own fixture correctly (confirmed 0/0 for its `staff_submissions`/`staff` rows by SQL immediately after) — the bug is isolated to the assertion being unscoped, not to a leak in the spec's teardown.

## Suspected cause
`e2e/office/join-approve-handoff.spec.ts:114` — the locator `adminPage.getByRole("button", { name: "Approve", exact: true })` matches every pending submission's card, not just the one this spec created. It should scope to the applicant's own card, e.g. re-derive the same `card` locator used at line 104-106 (`adminPage.getByText(APPLICANT_NAME, { exact: true }).locator(...)`) and assert that locator has count 0, or simply assert `adminPage.getByText(APPLICANT_NAME, { exact: true })` has count 0 after reload.

## Verify
Re-run `npx playwright test --project=setup --project=office e2e/office/join-approve-handoff.spec.ts` against staging with the standing "E2E Join Applicant" pending row still present (do not delete it — it belongs to `public/join.spec.ts`'s fixture, not a QA marker row) — all 3 tests in the file must pass.

## Fix
`e2e/office/join-approve-handoff.spec.ts` line 114: the queue-empty assertion after
approval was `getByRole("button", { name: "Approve", exact: true })` → count 0 — a
page-wide count that fails whenever any OTHER submission is pending (the standing,
by-design state left by `e2e/public/join.spec.ts`'s "E2E Join Applicant" fixture).
Replaced with a count-0 assertion on `getByText(APPLICANT_NAME, { exact: true })`,
scoping the check to this spec's own applicant card exactly as the earlier steps in
the same test already do (lines 100, 104-106). Safe: test-only change, no app code,
no fixture/teardown changes; the assertion still proves the approved card left the
queue, it just no longer depends on cross-suite execution order. The fix is to the
spec itself, so the spec is its own regression test — before the change it fails
("Expected 0, Received 1") whenever the join fixture's pending row exists, per the
live staging run in Evidence; after it, the other card no longer matches the locator.

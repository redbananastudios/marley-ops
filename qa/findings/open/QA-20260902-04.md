## Summary
The staging takepayments merchant sandbox (292749) rejects every one of takepayments' own officially documented test card numbers with the same generic gateway-level error, regardless of card scheme or the card's intended test outcome (authorised vs. declined). This means nobody can currently produce a genuine sandbox card charge on staging — the `/q/<token>` accept-and-pay-deposit flow can be exercised right up to the Hosted Payment Page hand-off, but the actual card capture step cannot be verified end to end by any automated or manual tester.

## Repro
1. Confirm `business_settings.card_payments_enabled = true` (brand-level `marley.card_payments_enabled` is already `true`; the global flag was found `false` on staging at test time — see note below).
2. Accept a `sent` quote via `/q/<token>` (marker quote, e.g. `quote_ref=QA-SENTINEL-36705170`), reach the "Quote accepted — one last step" screen, click "Pay £100 deposit by card →".
3. Land on the real takepayments Hosted Payment Page (`https://gw1.tponlinepayments.com/paymentform/`), correctly pre-filled: "Secure Payment to: MARLEY MOVES", "Order Reference: QA-SENTINEL-36705170 Deposit", "Purchase Amount: GBP 100.00".
4. Submit each of takepayments' own published test cards (from their "Test cases takepayments gateway V1.1" reference):
   - `4976000000003436` (Visa, documented as Test Case 1 — should authorise)
   - `5100000000005460` (MasterCard, documented as Test Case 1 — should authorise)
   - `4221690000004963` (Visa, documented as Test Case 2 — should decline)
5. Expected: at least the "should authorise" cards settle successfully, so `quotes.deposit_paid_at` / `deposit_paid_method='card'` / `card_payments.status='paid'` can be verified.
6. Actual: all three attempts are rejected identically — `status='failed'`, `response_code=65566`, `response_message="Disallowed cardnumber"` — independent of scheme or intended outcome. This is a merchant-account-level allowlist block, not a real card decline.

## Evidence
`card_payments` rows for the three attempts (service-role read-back), all `status: 'failed'`, `response_code: 65566`, `response_message: "Disallowed cardnumber"`.

`e2e/fixtures/sandbox-cards.ts` lines 1-14: `E2E_CARD_APPROVED` / `E2E_CARD_DECLINED` are unset (empty), with the file's own comment saying to "fill them in from the merchant sandbox console when wiring the card scenarios" — this was evidently never done for merchant 292749. The generic takepayments test-card PDF is apparently not what is actually provisioned/allow-listed on this specific merchant sandbox account, so no one has ever completed a real card payment against staging merchant 292749.

## Suspected cause
Not a code defect in `marley-ops` — the accept flow, signature/terms recording, deposit-invoice creation, and HPP hand-off (amount, reference, order description) all verified correct up to the point of hand-off to takepayments. The blocker is external: merchant 292749's sandbox configuration on takepayments' side does not accept the standard published test card numbers. This needs either (a) the correct test card numbers for THIS specific merchant sandbox pulled from the takepayments merchant portal / account manager, or (b) confirmation from takepayments that merchant 292749's sandbox needs reconfiguring to accept standard test cards. Either way this is an external account-configuration fix, not something the repair loop can act on — hence `risky`, for Peter.

## Note (process, not part of the finding)
`business_settings.card_payments_enabled` (the global flag) was found `false` on staging at test time, even though brand `marley.card_payments_enabled=true`. The role agent flipped it to `true` to reach the card step and reverted it to `false` afterward (confirmed by the main loop's independent read-back post-run: `{id: true, card_payments_enabled: false}`). Flagging only because it's a global setting, not a marker row — future runs touching it should keep doing exactly this (read-before, revert-after, verify).

## Verify
Once the correct test-card numbers for merchant 292749's sandbox are known (from Peter/takepayments), repeat the repro above with those numbers: an "authorised" test card must produce `card_payments.status='paid'`, `quotes.deposit_paid_at` set, `deposit_paid_method='card'`. Until then, the `/q` accept-flow card path cannot be fully regression-tested on staging — the next audit run should re-attempt this exact repro to see if it still fails identically.

## Summary
Admin's "Return for changes" action on a submitted contractor statement reports success in the UI (success toast, dialog closes) but does not durably update the statement — it stays `status='submitted'` in the database, so the crew never actually receives it back as a draft to amend.

## Repro
1. This is CI's own permanent spec, not a manually driven repro: `e2e/office/contractor-pay.spec.ts` — "Office — Contractor pay (review a submitted invoice) › return a submitted invoice to the crew with a reason". CI's own seed (`scripts/seed-e2e.mjs`) creates a single `staff` row "E2E Pay Crew" with one `staff_statements` row (`ref=MMP-E2E01`, `status=submitted`).
2. Admin login (CI's `e2e-office@marleymoves.test`, role confirmed `admin` via live query) → `/finance/statements` → open the "E2E Pay Crew" row → Return → fill a reason → "Return for changes". No error toast is asserted by the test at this step, only that the flow completes.
3. Expected (the spec's own assertion): the row disappears from the default "submitted" filter — `getByText('E2E Pay Crew')` count 0 within 15s, because `returnStatementToCrewAction` sets `status='draft'`.
4. Actual: `getByText('E2E Pay Crew')` stays at count 1 for the full 15s window — the row never leaves "submitted".

Reproduced on **two independent CI runs**, 8 minutes apart, on two different commits with **no code changes to the statements action, the office view, or the spec between them**:
- push run [32447552408](https://github.com/redbananastudios/marley-ops/actions/runs/32447552408) on `bb76bc7e` (2026-08-21 04:36 UTC) — e2e job failed, same assertion.
- workflow_dispatch run [32448046368](https://github.com/redbananastudios/marley-ops/actions/runs/32448046368) on `ddd7479` (2026-08-21 04:45 UTC, the sha currently deployed to staging) — e2e job failed, identical assertion, identical locator/count.
- `git diff --stat 1f4a65f bb76bc7e` (last known-good run → first failing run) touches only `e2e/crew/invoicing-submit-lines.spec.ts`, `e2e/estimator/pay-statement.spec.ts`, docs/ledger files — **zero changes** to `app/(dashboard)/finance/statements/actions.ts`, `components/finance/office-statements-view.tsx`, or `e2e/office/contractor-pay.spec.ts` itself. The break is not explained by a code diff in this window.
- `test` job (lint/tsc/vitest) passed clean on both failing runs — this is an e2e-only, live-staging-only failure.

Only one staff row and one statement exist (no duplicate-row explanation for the stuck count). `returnStatementToCrewAction` (`app/(dashboard)/finance/statements/actions.ts:61-85`) unconditionally sets `returned_at`/`return_reason` on any row it actually updates — their being null proves the `UPDATE ... WHERE id = ? AND status = 'submitted'` never matched/committed a row, even though the test did not fail at the "Return for changes" click (the spec doesn't assert `r.ok` from the browser side — a silent `ok:false` from the server action would surface only as an unread toast, then fail one step later at the count assertion, which is exactly the observed shape).

## Suspected cause
Not yet isolated to a line — `git diff` rules out the obvious files, so this needs the repair agent to check things a diff can't show: RLS policy behaviour on `staff_statements` UPDATE+`.select()` for the `admin` role specifically in the CI/staging environment (a policy that permits the UPDATE but not reading the row back in the same statement would make Supabase report `data: []` and the action would return `ok:false` "Only a submitted statement can be returned." even though the WHERE clause matched), or a session/cookie timing issue specific to the server action being called from a freshly-hydrated dialog in this CI environment. `app/(dashboard)/finance/statements/actions.ts:61-85` (`returnStatementToCrewAction`) and its RLS policy on `staff_statements` are the places to start.

## Verify
Re-run `e2e/office/contractor-pay.spec.ts` against deployed staging (or the exact repro above): after "Return for changes", `staff_statements.status` for the target row must be `draft` with `returned_at` and `return_reason` set, and the row must leave the office "submitted" filter.

## Summary
The lead-delete guard's "it has a storage let" protection is effectively dead code for real data: `canDeleteLead` counts `storage_lets` by `.eq("lead_id", id)`, but the only real INSERT path (`startLetAction` in `app/(dashboard)/storage/actions.ts`) never sets `storage_lets.lead_id` — it only takes a `client_id`. Every genuine storage-business display surface (`/storage`, `/performance`, `/s/[token]`) also keys storage lets to a customer by `client_id`, never `lead_id`. So a lead whose client has a real, active storage unit under contract can pass the delete guard freely, because the count the guard reads is always 0 in practice.

## Repro
1. Service-role SQL, staging, 2026-08-20: `select column_name, is_nullable from information_schema.columns where table_name='storage_lets'` — `client_id` is `NOT NULL`, `lead_id` is nullable.
2. Grep `app/(dashboard)/storage/actions.ts` `startLetAction` (the only INSERT into `storage_lets` in the app): the insert payload sets `unit_id`, `client_id`, dates, rate — never `lead_id`.
3. Grep the three real display surfaces — `app/(dashboard)/storage/page.tsx:28`, `app/(dashboard)/performance/page.tsx:102`, `app/s/[token]/page.tsx:37` — all query `storage_lets` by `client_id`.
4. `app/(dashboard)/leads/actions.ts` `deleteLeadAction`'s `COUNTED` array checks `storage_lets` by `.eq("lead_id", id)` — for any storage let created through the real UI, this is 0, so `lib/leads/deletable.ts`'s `if (f.storageLets > 0) return { deletable: false, reason: "it has a storage let" }` never fires for genuine storage business.

## Evidence
Live-verified mechanically (a manually seeded `storage_lets` row with `lead_id` explicitly set correctly triggers the refusal — the column match itself works), but the population path that would make that count non-zero in real usage does not exist anywhere in the app.

## Suspected cause
`storage_lets.lead_id` is a nullable, effectively-vestigial column that the storage feature was never wired to populate; the delete guard was written assuming it would be.

## Why risky, not safe-fix
This is a business-history judgement call, not a mechanical bug: is a lead-level check even the right model for a client-level object like storage (a storage let deliberately outlives any one lead/enquiry)? The fix could be "count storage_lets by client_id instead" (broadens the refusal to ANY lead on a client with a storage let, which may be too broad — one of several leads on a client shouldn't necessarily be blocked from deletion by a sibling's storage business) or "populate lead_id on let creation" (a data-model change) or "leave as-is, storage isn't really lead-scoped so the guard's intent doesn't apply." Needs Peter's call, same class of decision as the money-classification findings (QA-20260820-03/-04).

## Verify
After Peter's decision on the intended model: seed a lead whose client has an active storage let (created via the real UI path, not a hand-set `lead_id`), attempt delete, and assert it is refused with a "storage let" reason (or that the chosen alternative behaviour holds).

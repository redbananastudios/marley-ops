## Summary
Own-domain recognition is widened with EVERY brands row, including the INACTIVE pitmans row, so live Marley inbound mail arriving from `pitmansremovals.co.uk` is now treated as robot/own-domain traffic and stops being forwarded to a human. Gate 13's commit message frames the change as "domain recognition only WIDENS" — but widening the own-domain set NARROWS the forward set. This is the one finding in the merge batch that changes LIVE Marley behaviour today, and it is not gated on `brand !== 'marley'`.

## Repro
1. A Marley (slug `marley`) customer or contact whose email address is on `pitmansremovals.co.uk` — entirely plausible mid-acquisition (Mark, or any Pitmans staffer booking a Marley move) — replies to their quote chase at `q-<token>@reply.marleymoves.co.uk`.
2. Expected (pre-gate-13 behaviour): `shouldForwardUnmatched` returns true, the reply is forwarded to the lead owner's mailbox, and the ops alert reads "<Customer> replied to a chase email... forwarded to the owner".
3. Actual: `ourDomains` now contains `pitmansremovals.co.uk` (the inactive Pitmans row is still returned by `listAllBrands`), so `robotSender` is true. The owner_forward email is never sent, the customer's words land only in the Comms tab, and the ops alert instead reads "An automated message hit the reply address".
4. Same for the unmatched branch: mail from that domain to a dead reply address is silently dropped instead of forwarded to hello@marleymoves.co.uk.

## Evidence
`app/api/webhooks/resend-inbound/route.ts:256` and `:373` build `ourDomains` from `listAllBrands` — ALL rows, not active ones. The pitmans row is seeded `active=false`, so this takes effect on the current single-brand production instance immediately on deploy, before pitmans is switched on.

## Suspected cause
`listAllBrands` was the right choice for surfaces that must recognise a brand regardless of activation, but own-domain recognition is a suppression list: adding to it removes a human from the loop. Either scope it to active brands, or keep all-brands recognition but preserve forwarding when the RECIPIENT brand differs from the sender's domain brand.

Filed `risky`: a customer reply silently not reaching a human is the "customer having to ask twice" class, and the fix is a judgement about which brand set the suppression should read.

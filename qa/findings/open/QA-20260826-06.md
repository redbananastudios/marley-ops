## Summary
Own-domain recognition is widened with EVERY brands row, including the INACTIVE pitmans row, so live Marley inbound mail arriving from `pitmansremovals.co.uk` is now treated as robot/own-domain traffic and stops being forwarded to a human. Gate 13's commit message frames the change as "domain recognition only WIDENS" — but widening the own-domain set NARROWS the forward set. This is the one finding in the merge batch that changes LIVE Marley behaviour today, and it is not gated on `brand !== 'marley'`.

## Repro
1. A Marley (slug `marley`) customer or contact whose email address is on `pitmansremovals.co.uk` — entirely plausible mid-acquisition (Mark, or any Pitmans staffer booking a Marley move) — replies to their quote chase at `q-<token>@reply.marleymoves.co.uk`.
2. Expected (pre-gate-13 behaviour): `shouldForwardUnmatched` returns true, the reply is forwarded to the lead owner's mailbox, and the ops alert reads "<Customer> replied to a chase email... forwarded to the owner".
3. Actual: `ourDomains` now contains `pitmansremovals.co.uk` (the inactive Pitmans row is still returned by `listAllBrands`), so `robotSender` is true. The owner_forward email is never sent, the customer's words land only in the Comms tab, and the ops alert instead reads "An automated message hit the reply address".
4. Same for the unmatched branch: mail from that domain to a dead reply address is silently dropped instead of forwarded to hello@marleymoves.co.uk.

## Evidence
`app/api/webhooks/resend-inbound/route.ts:256` and `:373` build `ourDomains` from `listAllBrands` — ALL rows, not active ones. The pitmans row is seeded `active=false`, so this takes effect on the current single-brand production instance immediately on deploy, before pitmans is switched on.

## Suspected cause
`listAllBrands` was the right choice for surfaces that must recognise a brand regardless of activation, but own-domain recognition is a suppression list: adding to it removes a human from the loop. Either scope it to active brands, or keep all-brands recognition but preserve forwarding when the RECIPIENT brand differs from the sender's domain brand.

Filed `risky`: a customer reply silently not reaching a human is the "customer having to ask twice" class, and the fix is a judgement about which brand set the suppression should read.

## Resolution (2026-08-28, branch `qa/comms-brand-identity`)

Confirmed still real, with one correction to the finding's own framing: this
does **not** change live behaviour today. Prod has no `pitmans` row (migration
`0104` is row 1 of the unapplied prod runbook) and gate 13 is not deployed
there; staging has the row flipped active, where the bug does not bite. The
exposure window is precise and real: **prod, from the promotion deploy until
someone flips `pitmans.active` true** - a gap the cutover plan deliberately
creates and which may run for days.

The code contradicted its own spec. PRD 11.7 trap 3 and `sender.ts`'s own
docstring both say widen to every **active** brand's domains; a second
docstring in the same file argued for all rows, and the implementation followed
that one.

**The insight that resolves it:** the two columns are not the same kind of
thing.

- `reply_domain` is a MACHINE domain. No human mailbox exists there, so
  counting it can never suppress a person. It stays counted for every row,
  active or not - that is the genuine loop guard the all-rows argument was
  reaching for.
- `email_domain` is a HUMAN staff domain, and only ours while we send from it.
  An inactive brand sends nothing, so adding its staff domain widens nothing
  useful. Recognising an address as ours is what STOPS it being forwarded, so
  widening the own-domain set narrows the forward set.

**Fixed** by putting that split inside `brandInboundDomains` rather than at the
call site, so a future caller cannot reintroduce it. Switching the call site to
`listActiveBrands` would have fixed the harm but lost the reply-domain guard.

**Known, deliberate residual:** once the brand IS active, its staff domain is
suppressed again, so a customer of one brand writing from another brand's staff
domain still is not forwarded. That is the same rule the default brand already
carries for its own staff, so it is consistent rather than new. Closing it
needs a recipient-brand comparison, which only works on the matched branch -
the unmatched branch has no brand signal at all, and that is the silent one.
Not recommended.

## Verify (updated)

`brandInboundDomains` over an inactive brand row must contain its reply domain
and NOT its email domain, and `shouldForwardUnmatched` for a person at that
email domain must be true. Unit-locked in `tests/lib/comms/sender.test.ts`,
including the converse for an active row and a guard that the default brand's
recognition is untouched either way.

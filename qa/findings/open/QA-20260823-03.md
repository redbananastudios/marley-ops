## Summary
When a `refund_queue` row's linked quote has no `customer_email` on file, `completeRefundQueueAction` correctly skips the customer email and instead fires an internal-only ops alert (`sendOpsAlert`, not logged in `communications`) — but the office UI's Complete button (labelled "Complete — send the refund email") and its success toast unconditionally say "Refund completed — customer emailed." regardless of which branch actually ran. The office has no way to tell a real customer notification from a silent internal-only fallback, and could reasonably believe the customer already knows their refund went out when they were never told anything.

## Repro
1. Admin login. Seed (service-role) a `refund_queue` row: `trigger:'marley_cancel'`, `held:[{rail:'bank_transfer', amount:60, at:..., label:'deposit'}]`, `conditional_amount:0`, `unconditional_amount:60`, `status:'pending'`, linked to a quote whose `customer_email IS NULL`.
2. `/refunds` → Mark refunded (bank transfer, type £60.00 to confirm) → row's rail shows Done.
3. Click Complete → confirm in dialog.
4. UI toast: "Refund completed — customer emailed." Row moves to History as "Refunded · £60.00".
5. No new `communications` row exists for the customer (checked by `lead_id`/`quote_id`).

## Evidence
`app/actions/refunds.ts:645-683`: `if (quote?.customer_email && lines.length) { dispatchComm(...) } else if (!quote?.customer_email) { sendOpsAlert("Refund completed with no customer email on file...") }` — the else branch sends only to internal ops, via `sendEmail()` directly (not through `dispatchComm`, so it never lands a row in `communications`).

`components/refunds/execute-card.tsx:345,380`: trigger button text "Complete — send the refund email" and success toast "Refund completed — customer emailed." are both static strings, independent of the actual branch taken server-side; `completeRefundQueueAction`'s return type (`RefundActionResult`) carries no field distinguishing "customer emailed" from "no email on file, ops alerted instead".

SQL (this run, marker row, deleted after): `refund_queue.status='refunded'`, `events_log` has `rail_refunded`+`refunded` rows exactly as expected; `communications` table has zero rows for this refund/lead.

## Suspected cause
`completeRefundQueueAction`'s return value needs to carry which branch fired (e.g. `emailedCustomer: boolean`) so the client can show an accurate outcome.

## Fix shipped (2026-08-23)

`completeRefundQueueAction` and `retainRefundQueueAction` now return a
`customerNotice` describing what actually happened, and the dialogs render it
instead of asserting "customer emailed." on every branch. Anything other than a
clean send is a warning toast held for 12s, not a success.

Reading the branch turned up a case the finding did not name: on the Complete
path a quote WITH an email but no refund lines fell between the `if` and the
`else if`, so neither the customer nor ops heard anything at all. That is now
`nothing_to_send` and raises its own ops alert.

The same defect was present on RETAIN (`app/actions/refunds.ts:776` and the
"Outcome recorded — customer emailed." toast); fixed in the same pass.

An absent notice makes NO claim rather than defaulting to "emailed" — a default
of "sent" is exactly how this bug would rebuild itself. Covered by
`tests/lib/refunds/customer-notice.test.ts` (10 tests, mutation-verified:
reinstating the old behaviour fails 3 of them).

## Verify
Repeat the repro against a `refund_queue` row whose quote HAS a `customer_email` and confirm the toast still correctly says "customer emailed" there (the fix must not regress the true-positive path); against a null-email quote, confirm the UI no longer claims a customer email was sent.

## Summary
CI's e2e job on staging is red (has been since at least commit `6ddf711`, the prior audit's own push) because `scripts/seed-e2e.mjs`'s `wipe()` deletes `surveys` rows before deleting the `appointments` rows that reference them via `appointments.survey_id`, so any leftover E2E `survey`-type appointment causes the wipe to die on a foreign-key violation before it can clean anything up — and because the script `process.exit(1)`s on that error, the offending rows are never removed, so the failure is permanent and self-perpetuating: every future push's e2e job will fail the identical way until this is fixed or the stuck rows are manually cleared.

## Repro
1. No login needed — this is server-side seed tooling, reproduced by CI itself.
2. GitHub Actions run `32573348862` ("CI + Deploy to Staging" on `staging`, sha `6ddf711`), job `e2e` (id `97032344617`), step "Run node scripts/seed-e2e.mjs".
3. Expected: wipe clears all rows named `E2E %`/`QA-SENTINEL` and seeding proceeds, e2e job goes green. Actual: step fails immediately with:
   ```
   wipe surveys update or delete on table "surveys" violates foreign key constraint "appointments_survey_id_fkey" on table "appointments"
   ##[error]Process completed with exit code 1.
   ```
   The Playwright test step is then skipped entirely (never runs a single spec), and the whole workflow run reports `conclusion: failure`.
4. This is not a one-off flake: the "test" job (lint/tsc/vitest) on the same sha passed clean, and `deploy-staging` also passed — only the e2e job's seed step fails, on a deterministic FK ordering bug, against real leftover data (see Evidence). Re-running would fail identically until the stuck row is cleared or the order is fixed.

## Evidence
Read-only query against staging via service-role client (no rows created/altered by this check):
```
E2E leads: 18 (incl. "E2E Estimator Work Quote 1787388365086")
appointments for those leads:
  { id: '2fa23680-...', lead_id: 'c44c127b-...', survey_id: 'c75057e2-...', appt_type: 'survey' }
surveys with lead_id in E2E leads:
  { id: 'c75057e2-925d-4d84-b21d-23967d35fc7c', lead_id: 'c44c127b-a76b-4008-9349-d3da1f5d6293' }
```
`scripts/seed-e2e.mjs:114-128` (`LEAD_CHILD_TABLES`) lists `"surveys"` as one of the tables wiped in the loop at `:136-140`, filtered only by `.eq("lead_id", ...)` — this runs and deletes `surveys` **before** line 145's `sb.from("appointments").delete().in("lead_id", leadIds)`. The lingering survey-type appointment above still points at that `surveys` row via `survey_id` (a separate FK from the `lead_id` relationship the loop orders on), so deleting the survey first is rejected by Postgres. The die()/process.exit(1) at `:104-107` then aborts before the appointment (and everything after it in `wipe()`) is ever deleted, so the row that broke the run survives to break the next one too.

## Suspected cause
`scripts/seed-e2e.mjs:114-145` — `wipe()`'s child-table loop treats `surveys` as safe to delete alongside the other `lead_id`-scoped children, but `appointments.survey_id` is a second, deeper FK into `surveys` that the current "deepest first" ordering doesn't account for (the comment at `:113` claims deepest-first but the array doesn't put `appointments` ahead of `surveys`). Fix needs either: delete/null `appointments.survey_id` (or delete the appointments themselves) before the `surveys` delete in the loop, or move `surveys` out of `LEAD_CHILD_TABLES` and delete it in the post-appointments block alongside `quotes`/`leads` at `:145-147`.

## Verify
Re-run (or wait for) a staging CI run's `e2e` job and confirm the "Run node scripts/seed-e2e.mjs" step completes without the `appointments_survey_id_fkey` error and the Playwright step actually executes (not `skipped`). Cross-check: `SELECT id FROM appointments WHERE survey_id = 'c75057e2-925d-4d84-b21d-23967d35fc7c'` and the matching `surveys` row should both be gone after a clean seed run against that same lead name, proving the reordered wipe actually clears this shape of data rather than merely avoiding it.

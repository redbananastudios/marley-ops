## Summary

An estimator login can navigate directly to `/jobs`, `/clients`, `/board`, `/storage`, `/performance`, `/automations`, or `/documents` and see the full, unredacted page — all customer PII, cross-staff pay/margin figures, company-wide financials, and signed documents — with no redirect, no 403, nothing. Access control for these seven routes exists only as hidden nav links (they're simply omitted from `ESTIMATOR_NAV`), which is exactly the anti-pattern the codebase's own comments elsewhere warn against. **Confirmed the same missing gate exists on `master` (production)** — this is not staging-only.

## Repro

1. Role + login: marker estimator user `qa-sentinel-20260827-estimator-mdl2o6@marleymoves.invalid` (profile id `fd15dbdb-04a9-4584-b07e-6f378d2b50f8`, role=`estimator`) on `https://staging.ops.marleymoves.co.uk`.
2. After logging in and landing at `/estimator`, navigate directly (address bar / `page.goto`) to each of:
   - `https://staging.ops.marleymoves.co.uk/jobs`
   - `https://staging.ops.marleymoves.co.uk/clients`
   - `https://staging.ops.marleymoves.co.uk/board`

   - `https://staging.ops.marleymoves.co.uk/performance`
   - `https://staging.ops.marleymoves.co.uk/automations`
   - `https://staging.ops.marleymoves.co.uk/documents`

## Evidence

Source read on the `staging` checkout (`/home/user/marley-ops`), confirmed independently by the main loop after the role agent's report:

- `app/(dashboard)/layout.tsx:19-20` — the only role check in the shared layout: `if (profile.role === "crew") redirect("/my-jobs");`. Nothing else gates estimator (or any other authenticated role) out of any nested route.
- None of these seven `page.tsx` files call `requireOfficeProfile()` or check `profile.role` themselves:
  - `app/(dashboard)/jobs/page.tsx` (`CompletedJobsPage`)
  - `app/(dashboard)/clients/page.tsx` (`ClientsPage`)
  - `app/(dashboard)/board/page.tsx` (`BoardPage`)
  - `app/(dashboard)/storage/page.tsx` (`StoragePage`)
  - `app/(dashboard)/performance/page.tsx` (`PerformancePage`)
  - `app/(dashboard)/automations/page.tsx` (`AutomationsPage`)
  - `app/(dashboard)/documents/page.tsx` (`DocumentsPage`)
- Contrast: `app/(dashboard)/refunds/page.tsx:29-31` states the house rule explicitly in a comment: *"ADMIN-ONLY, gated server-side here AND in every action — nav is never the security boundary (the /finance/statements pattern)."* `/finance`, `/finance/statements`, `/refunds` all correctly self-gate; the 7 listed above do not.
- **Production check**: `git diff origin/master:"app/(dashboard)/layout.tsx" origin/staging:"app/(dashboard)/layout.tsx"` → identical. `git diff origin/master:"app/(dashboard)/automations/page.tsx" origin/staging:"..."` → identical. The other 5 pages differ from master only in unrelated brand-filter code (`grep -n "requireOfficeProfile\|getSessionProfile\|role !== \|role ===" <path>` on the `origin/master` copy of each of the 7 files returns **zero** role-gate hits, same as staging) — the missing gate is present on `master` too, i.e. live in production today.
- These routes read through the session-scoped `createClient()` (not service-role), so this isn't an RLS bypass exploit — it means RLS on the underlying tables (`leads`, `clients`, `appointments`, `staff`, etc.) does not restrict by role either, so the unfiltered dataset comes straight back once the page itself fails to gate.

## Suspected cause

`app/(dashboard)/layout.tsx:19-20` gates only `role === "crew"`; the 7 listed `page.tsx` files never call `requireOfficeProfile()` (compare `app/(dashboard)/claims/page.tsx:57-58`, `app/(dashboard)/content/page.tsx:35-36`, `app/(dashboard)/refunds/page.tsx:29-31` — the working pattern already exists in the codebase, just wasn't applied to these 7 pages).

As a fresh estimator-role login (any role != admin), `page.goto()` to each of `/jobs`, `/clients`, `/board`, `/storage`, `/performance`, `/automations`, `/documents` on staging and confirm each redirects away (matching whatever the eventual fix does — e.g. to `/estimator` or `/estimator/pay`) with none of the current page content reaching the DOM.

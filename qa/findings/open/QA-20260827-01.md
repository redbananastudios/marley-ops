## Summary

An estimator login can navigate directly to `/jobs`, `/clients`, `/board`, `/storage`, `/performance`, `/automations`, or `/documents` and see the full, unredacted page — all customer PII, cross-staff pay/margin figures, company-wide financials, and signed documents — with no redirect, no 403, nothing. Access control for these seven routes exists only as hidden nav links (they're simply omitted from `ESTIMATOR_NAV`), which is exactly the anti-pattern the codebase's own comments elsewhere warn against. **Confirmed the same missing gate exists on `master` (production)** — this is not staging-only.

## Evidence

Source read on the `staging` checkout (`/home/user/marley-ops`), confirmed independently by the main loop after the role agent's report:

- `app/(dashboard)/layout.tsx:19-20` — the only role check in the shared layout: `if (profile.role === "crew") redirect("/my-jobs");`. Nothing else gates estimator (or any other authenticated role) out of any nested route.
- None of these seven `page.tsx` files call `requireOfficeProfile()` or check `profile.role` themselves:
  - `app/(dashboard)/jobs/page.tsx` (`CompletedJobsPage`)
  - `app/(dashboard)/clients/page.tsx` (`ClientsPage`)
  - `app/(dashboard)/board/page.tsx` (`BoardPage`)
  - `app/(dashboard)/storage/page.tsx` (`StoragePage`)
  - `app/(dashboard)/performance/page.tsx` (`PerformancePage`)
  - `app/(dashboard)/automations/page.tsx` (`AutomationsPage`)
  - `app/(dashboard)/documents/page.tsx` (`DocumentsPage`)
- Contrast: `app/(dashboard)/refunds/page.tsx:29-31` states the house rule explicitly in a comment: *"ADMIN-ONLY, gated server-side here AND in every action — nav is never the security boundary (the /finance/statements pattern)."* `/finance`, `/finance/statements`, `/refunds` all correctly self-gate; the 7 listed above do not.
- **Production check**: `git diff origin/master:"app/(dashboard)/layout.tsx" origin/staging:"app/(dashboard)/layout.tsx"` → identical. `git diff origin/master:"app/(dashboard)/automations/page.tsx" origin/staging:"..."` → identical. The other 5 pages differ from master only in unrelated brand-filter code (`grep -n "requireOfficeProfile\|getSessionProfile\|role !== \|role ===" <path>` on the `origin/master` copy of each of the 7 files returns **zero** role-gate hits, same as staging) — the missing gate is present on `master` too, i.e. live in production today.
- These routes read through the session-scoped `createClient()` (not service-role), so this isn't an RLS bypass exploit — it means RLS on the underlying tables (`leads`, `clients`, `appointments`, `staff`, etc.) does not restrict by role either, so the unfiltered dataset comes straight back once the page itself fails to gate.

## Suspected cause

`app/(dashboard)/layout.tsx:19-20` gates only `role === "crew"`; the 7 listed `page.tsx` files never call `requireOfficeProfile()` (compare `app/(dashboard)/claims/page.tsx:57-58`, `app/(dashboard)/content/page.tsx:35-36`, `app/(dashboard)/refunds/page.tsx:29-31` — the working pattern already exists in the codebase, just wasn't applied to these 7 pages).

## Verify

As a fresh estimator-role login (any role != admin), `page.goto()` to each of `/jobs`, `/clients`, `/board`, `/storage`, `/performance`, `/automations`, `/documents` on staging and confirm each redirects away (matching whatever the eventual fix does — e.g. to `/estimator` or `/estimator/pay`) with none of the current page content reaching the DOM. ## Fix (2026-08-27, `fix/office-route-role-gates`)

All seven pages now call `requireAdminPage()` as their first statement.

- `lib/auth.ts`: new `requireAdminPage()` — `!profile` → `/auth/stale` (matching
  the layout, since `/login` redirect-loops against an authenticated session),
  `crew` → `/my-jobs`, any other non-admin → `/estimator`. One helper rather
  than seven copied conditionals: a gate that must be remembered per page is a
  gate that gets forgotten on page eight.
- `app/(dashboard)/{jobs,clients,board,storage,performance,automations,documents}/page.tsx`:
  gate added as the first statement. On `/performance` it precedes the
  `sp.tab` dispatch, so the Sales and Storage tab components are covered too —
  gating after the dispatch would have left two of the three tabs open.
- `app/(dashboard)/clients/[id]/page.tsx`: the "Clients" crumb and the "All
  documents" link now render for admins only. That record page stays
  estimator-readable on purpose, so without this the fix would have left an
  estimator looking at two links that do nothing but bounce them out of the
  page they were working in. Every other in-app link to the seven sits on a
  surface an estimator already cannot reach (the dashboard root redirects them;
  `/performance` is now gated) — checked, not assumed.

**Deliberately NOT changed**, having read each one rather than pattern-matching
the route list:

- `/clients/[id]` and `/resources` read the role and withhold the admin-only
  parts (edit controls; crew pay rates, which RLS also withholds). The estimator
  reaches both legitimately while quoting. Making them admin-only would have
  broken that workflow and silently reversed a deliberate design.
- `/claims`, `/claims/[id]`, `/content` gate on `requireOfficeProfile()` — an
  explicit decision to admit the estimator, not the same defect.
- `/schedule/removals` remains ungated: absent from `ESTIMATOR_NAV` but reached
  by design from the surveys view the estimator does have, and carrying no pay,
  margin or bulk PII.

## Preventing page eight

The audit found seven; the same reasoning over the full route table found four
more routes worth reading (three of which turned out to be deliberate, above).
That gap is the actual defect — enforcement lived in reviewers' memory.

`tests/config/dashboard-route-gates.test.ts` now derives each page's level from
its own source and asserts it against a checked-in map of all 36 dashboard
routes. A page whose gate changes fails; **a new page with no entry also fails**,
so classifying a new office surface is a step on the way in rather than an audit
finding months later. Its last assertion states the property that failed here:
nothing outside the estimator's sidebar may be readable by typing its URL.

`e2e/estimator/gating.spec.ts` — the seven assertions the audit shipped skipped
are now live, so the gate is proven against a real estimator session on staging
rather than only in source.

## Summary
A lead's "Contact" card shows the shared `client` record's name/phone/email/postcode instead of this lead's own values (disagreeing with the page's own header), and saving an edit to one lead silently overwrites those fields on the shared client — changing what every OTHER lead attached to that client displays.

## Repro
1. Admin login (any office/admin account) → `/leads/new`. Create lead A with phone/email that match an existing client (dedup matches it — shown as an advisory banner "Matched existing client X").
2. Open lead A's detail page (`/leads/[id]`). The `<h1>` header correctly shows lead A's own `name`. Scroll to the "Contact" card: its **Name** field shows the *other, pre-existing* client's `display_name` — not lead A's name — with no label distinguishing the two sources.
3. Click Edit → change lead A's name → Save.
4. Reload lead B (any other lead sharing the same `client_id`). Lead B's own Contact card "Name" now also shows lead A's newly-edited name, even though lead B's own `leads.name` was never touched.

Concretely reproduced on staging (2026-08-19) with three leads sharing one client:
- `leads.1be79555-...` name = "QA-SENTINEL Admin Lead" → client `b7c4fdaf-...`
- Before edit: `clients.b7c4fdaf-....display_name` = "QA-SENTINEL Estimator Survey Lead" (a DIFFERENT lead's name — from another lead sharing the client)
- After editing lead `1be79555-...` to "QA-SENTINEL Admin Lead EDITED": `clients.b7c4fdaf-....display_name` becomes "QA-SENTINEL Admin Lead EDITED", and lead `7027d61f-...` ("QA-SENTINEL Estimator Survey Lead")'s own Contact card now shows "QA-SENTINEL Admin Lead EDITED" as its Name — despite `leads.7027d61f-....name` being unchanged.
- A third, freshly-created lead (`913ce3ad-...`) that deduped onto the same client immediately displayed "QA-SENTINEL Admin Lead EDITED" as its Name before it was ever edited.

## Evidence
Source, read 2026-08-19:
- `app/(dashboard)/leads/[id]/page.tsx:358` — header: `<h1>{lead.name ?? "Unnamed lead"}</h1>` (per-lead, correct).
- `app/(dashboard)/leads/[id]/page.tsx:475` — Contact card: `<Fact label="Name" value={client?.display_name ?? lead.name} />` (prefers the SHARED client's name over this lead's own `name`; same pattern for Phone/Email/Postcode on the next three lines).
- `app/(dashboard)/leads/actions.ts:374-385` (`updateLeadDetailsAction`) — on every lead save:
  ```
  if (lead?.client_id) {
    await sb.from("clients").update({
      display_name: v.name,
      phone_raw: v.phone || null,
      phone_e164: normalizePhone(v.phone),
      email: v.email || null,
      postcode_home: v.from_postcode || null,
    }).eq("id", lead.client_id);
  }
  ```
  This runs unconditionally whenever a lead is saved, with no check for whether other `leads` rows share `client_id` — a comment above it ("Keep the linked client's core contact aligned with the correction") shows the intent (fixing a bounced/wrong address) but the write has no scope to "this correction only concerns this lead."

SQL used to confirm (service role, staging):
```sql
select id, name, client_id from leads where id in ('1be79555-...', '7027d61f-...', '913ce3ad-...');
select id, display_name from clients where id = 'b7c4fdaf-...';
```
Observed exactly as described above — matches the repro steps.

## Suspected cause
`app/(dashboard)/leads/[id]/page.tsx:475-478` reads client fields as the primary source with lead fields only as fallback (should likely be the reverse — the lead's own captured details are what this lead's page is about); `app/(dashboard)/leads/actions.ts:374-385` writes the client row on every lead edit with no guard for shared clients (should either scope the write to when this IS the only/primary lead on the client, or the UI should make clear it's editing the shared account record, not just this enquiry).

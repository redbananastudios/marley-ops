## Summary
`smsSenderFor` falls back to the Marley WebEx alphanumeric sender id for a non-default brand whose `sms_sender` is null — the exact cross-brand fallback that `templateIdFor`, added in the SAME commit, was written to forbid. So a customer is chased for money by a brand name they have no relationship with, and their reply lands on the wrong brand's SMS rail.

## Repro
1. A non-default brand with `sms_sender` null (the current seeded state).
2. Trigger a deposit-reminder or balance-reminder SMS (`lib/comms/templates.ts` — `depositReminderTemplate` / `balanceReminderTemplate`).
3. Expected: the message is not sent, or is sent from that brand's own sender — consistent with `templateIdFor`, which refuses to fall back to another brand's template.
4. Actual: the body correctly reads "Hi X, <Brand> here. A quick reminder the £N deposit is still outstanding…" but it is DELIVERED from `WEBEX_SMS_SENDER_MARLEY_MOVES`. The customer sees a money chase from "MarleyMoves" about a booking they have no record of; replies route to Marley's rail.

## Evidence
`lib/comms/send.ts:227`. The function's own comment documents the fallback as deliberate — but it is a live cross-brand identity fallback on a payment-chase channel, sitting beside a template path in the same commit that refuses the identical fallback for the same reason. The two cannot both be right.

## Suspected cause
The SMS sender predates the brand layer and its fallback was kept for continuity; `templateIdFor`'s stricter contract was written later in the same gate without revisiting it. Fix is to match `templateIdFor`: no per-brand sender configured means no send (and a logged skip), not someone else's identity — the same rule already applied to `review_url` (no review_url = no review email).

Filed `risky`: it is a money-chase channel and the change stops sends that currently succeed, so the trade-off is Peter's.

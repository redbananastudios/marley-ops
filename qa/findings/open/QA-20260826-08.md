## Summary
`smsSenderFor` falls back to the Marley WebEx alphanumeric sender id for a non-default brand whose `sms_sender` is null — the exact cross-brand fallback that `templateIdFor`, added in the SAME commit, was written to forbid. So a customer is chased for money by a brand name they have no relationship with, and their reply lands on the wrong brand's SMS rail.

## Repro
1. A non-default brand with `sms_sender` null (the current seeded state).
2. Trigger a deposit-reminder or balance-reminder SMS (`lib/comms/templates.ts` — `depositReminderTemplate` / `balanceReminderTemplate`).
3. Expected: the message is not sent, or is sent from that brand's own sender — consistent with `templateIdFor`, which refuses to fall back to another brand's template.
4. Actual: the body correctly reads "Hi X, <Brand> here. A quick reminder the £N deposit is still outstanding…" but it is DELIVERED from `WEBEX_SMS_SENDER_MARLEY_MOVES`. The customer sees a money chase from "MarleyMoves" about a booking they have no record of; replies route to Marley's rail.

## Evidence
`lib/comms/send.ts:227`. The function's own comment documents the fallback as deliberate — but it is a live cross-brand identity fallback on a payment-chase channel, sitting beside a template path in the same commit that refuses the identical fallback for the same reason. The two cannot both be right.

## Suspected cause
The SMS sender predates the brand layer and its fallback was kept for continuity; `templateIdFor`'s stricter contract was written later in the same gate without revisiting it. Fix is to match `templateIdFor`: no per-brand sender configured means no send (and a logged skip), not someone else's identity — the same rule already applied to `review_url` (no review_url = no review email).

Filed `risky`: it is a money-chase channel and the change stops sends that currently succeed, so the trade-off is Peter's.

## PARTIAL FIX 2026-08-26 — the live exposure is closed, the defect is NOT. Stays open.

Peter created a WebEx Interact alphanumeric sender named **Pitmans** on 2026-08-26, and
migration `0107_pitmans_sms_sender.sql` sets `brands.sms_sender = 'Pitmans'` on the pitmans
row. Applied and verified on staging: `pitmans` = `Pitmans`, `marley` and `group` still
`<null>` (correct — `smsSenderFor()` never reads the column for the default brand). Runbook
row 4 added so it reaches prod on the 18 September promotion.

**What that fixes:** a Pitmans deposit or balance chase is no longer delivered fronted by
Marley's sender id, and replies no longer land on Marley's SMS rail. That was the concrete
customer-facing harm, and it is gone as soon as this migration is applied.

**What it does NOT fix, and why this finding stays `open`:** the fallback in
`lib/comms/send.ts` is unchanged —

    return brandSender || process.env.WEBEX_SMS_SENDER_MARLEY_MOVES || process.env.WEBEX_SMS_SENDER;

so ANY future brand whose `sms_sender` is still a Phase-0 blank silently borrows Marley's
identity on a money-chase channel, exactly as Pitmans did. Populating one row does not
change the rule; it removes today's only instance of it. Closing the finding here would be
the "clear the surface that would have shown the problem" mistake — brand 3 would hit this
with nothing left on file to warn anyone.

**The remaining decision is Peter's, not automation's** (which is why it is still
`class: risky`): making it fail closed — no per-brand sender means no send, plus a logged
skip, matching `templateIdFor` and the `review_url` rule — STOPS sends that currently
succeed. That is a behaviour change on a payment-chase channel and needs his call.

Owner: Peter. Decide by the 18 September promotion, since after that a third brand becomes
a realistic prospect and the fail-open path reaches prod either way.

## Resolution (2026-08-28, branch `qa/comms-brand-identity`)

Confirmed still real. Migration `0107` set the seeded brand's `sms_sender`, so
the live INSTANCE is closed, but the fail-open `||` - the rule - was untouched,
which is what the finding said.

The two functions are not symmetric in consequence, and that decides the fix.
`templateIdFor` returning nothing costs the customer nothing: every call site
falls back to brand-aware inline HTML and the email still sends, correctly
branded. `smsSenderFor` returning nothing STOPS the send. So "refuse" and
"fail loudly" are the same option here, because the plumbing already makes a
refusal loud - `sendSms` returns a definite failure with no
`outcomeUnknown`, so the row is marked failed with no ambiguous re-drive
window, a `comm.provider.failed` issue is raised at severity error, and the
operator gets a toast on the click.

**Fixed: fail closed.** Under the old rule what reached the customer was a
money chase whose body named one brand and whose handset named another, with
their reply routed to a rail holding no record of them - visible only to them,
and only when they phoned. Under the new rule nothing reaches them and we find
out immediately.

**The group pseudo-brand is deliberately exempted.** `templateIdFor` needs no
group carve-out because an absent template degrades to inline HTML; here the
same shape would stop every group-branded SMS outright. Group comms keep the
operating company's identity by design.

The error message now names `brands.sms_sender` for a brand-scoped failure,
because the env vars are fine in that case and the generic wording would send
whoever reads the ops board to the wrong place.

**Note on the test:** the existing assertion read
`expect(smsSenderFor({ slug: "pitmans", smsSender: null })).toBe("Marley")`,
with a comment calling the fallback intended. It was the defect written down as
a spec, so it was replaced rather than refreshed.

## Follow-up raised separately

`checkWebex` in the Settings health card reads only the env pair and never

## Verify (updated)

`smsSenderFor` for a non-default brand with a null or empty `sms_sender` must
be undefined, the default brand and the group brand must still resolve through
the env chain, and `sendSms` for such a brand must return a definite failure
naming the column with no provider call made. Unit-locked in
`tests/lib/comms/send-idempotency.test.ts`.

## Summary
Editing ONLY a lead's postcode via the `/leads/[id]` Edit dialog updates `leads.from_postcode` (or `to_postcode`) correctly, but leaves the OLD postcode embedded, unchanged, inside the sibling `leads.from_address` (or `to_address`) text column — the two columns that together describe the same real-world pickup/drop-off address now disagree, and the lead-detail page's "Pickup address"/"Destination address" line still shows the stale postcode text even though the "Postcode" field and the "Route" line both show the new one.

## Repro
1. Role: admin (office login). Any marker lead works.
2. On `/leads/new`, hand-type a FULL address including postcode into the "from" side, e.g. street `12 test street`, town `bournemouth`, postcode `bh21 8nb`. Submit. Confirm `leads.from_postcode = "BH21 8NB"` and `leads.from_address = "12 test street, bournemouth, BH21 8NB"` (both correct at creation — the QA-20260827-05 create-path fix still holds).
3. Open `/leads/<id>`, click Edit. Note the dialog's "Postcode" field pre-fills `BH21 8NB` as expected, but its "Street address" field pre-fills the WHOLE raw stored string `12 test street, bournemouth, BH21 8NB` (postcode included) — already a visible duplication the moment the dialog opens.
4. Change ONLY the Postcode field, e.g. to `sp7 9px`. Leave the street address field untouched. Click Save.
5. Reload `/leads/<id>`.
6. Expected: both the "Postcode" field/"Route" line AND the "Pickup address" line reflect the new postcode (or at minimum stay internally consistent). Actual: "Postcode"/"Route" show `SP7 9PX`; "Pickup address" still reads `12 test street, bournemouth, BH21 8NB` — the OLD postcode, verbatim.

## Evidence
Live run against staging this session (Sonnet admin role-agent, main-loop independently confirmed the root cause by reading the source below — not just re-reading the agent's report). SQL read-back on the lead row after the edit+save (marker lead, deleted after):
```json
{ "from_postcode": "SP7 9PX", "from_address": "12 test street, bournemouth, BH21 8NB" }
```
`from_postcode` correctly holds the new value; `from_address` still contains the pre-edit postcode text unchanged — the same fact, two columns, in disagreement, matching AUDIT.md's own named "two-hats" bug class exactly.

## Suspected cause
`components/leads/edit-lead-dialog.tsx`:
- `seedAddress()` (~line 62-64) builds the dialog's structured address state as `{ line1: line, postcode }`, passing the RAW stored `from_address`/`to_address` string straight in as `line1` (called at ~line 108-109/115-116 as `seedAddress(initial.from_address, initial.from_postcode)`). Because the stored `from_address` already has the postcode text baked into it (by design, per the create-path formatter), `line1` now duplicates the postcode as plain text inside the address line the moment the dialog opens.
- `streetPart()` (~line 66-68) deliberately excludes `a.postcode` from what it writes back to `*_address` — this part of the design is correct in isolation (confirmed correct behaviour by a prior 2026-08-29 audit note) — but since `a.line1` already contains the OLD postcode as untouched text, `streetPart()` faithfully re-serializes that stale text back into `from_address` on every save, regardless of what the separate Postcode field was changed to. Editing only the postcode field can therefore never update the copy embedded in `*_address`.
- The fix is upstream of `streetPart()`: `seedAddress()` should split the raw stored address the way `lib/places/parse.ts`'s `addressFromLead(address, postcode)` already does — building `line1`/`town`/`county` WITHOUT the postcode baked in — exactly the pattern already used correctly for this identical column-pair shape in `app/(dashboard)/quotes/actions.ts:133-134`. Once `line1` no longer carries the postcode as text, a postcode-only edit naturally propagates through `streetPart()` on save.

## Verify
1. Create a lead with a full postcode-bearing address (as in Repro step 2).
2. Open the Edit dialog — the seeded "Street address" field must NOT visibly contain the postcode text.
3. Change only the Postcode field, save, reload.
4. `leads.from_address` (or `to_address`) must no longer contain the OLD postcode text, and the lead-detail page's address line must agree with the Postcode field/Route line — SQL and UI both consistent with the new postcode.

## Fix

Exactly the upstream fix the finding suggested. `seedAddress()` no longer dumps the raw
stored `*_address` string into `line1` — it parses the line through the existing shared
`addressFromLead()` (`lib/places/parse.ts`), the same helper `app/(dashboard)/quotes/actions.ts`
already uses for this identical column pair, so the baked-in postcode lands in the postcode
field and `line1`/`town`/`county` carry only the street text. When the parsed text and the
stored postcode column disagree (the stale rows this bug already wrote), the column wins —
it is what the Route line shows and what the dialog's Postcode field always prefiled. With
`line1` postcode-free, `streetPart()` (unchanged — its postcode exclusion was already
confirmed correct, 2026-08-29) naturally writes back a `*_address` that follows the Postcode
field on save, and a postcode-only edit also self-heals any pre-existing stale embedded text.

Both helpers moved to `lib/leads/edit-address.ts` (out of `edit-lead-dialog.tsx`) so the
seed→edit→streetPart round trip is unit-testable without the dialog's server-action import
graph; the dialog imports them from there, no behavioural change beyond the seeding itself.

Safe: pure client-side dialog state seeding + two-file lib/components diff, no schema, no
payments/comms/auth, no server action changes. Website-sync leads (postcode stored only in
the column, not the text) seed identically to before modulo the already-correct town split.

Test: `tests/lib/leads/edit-address.test.ts` — 6 assertions covering the finding's exact
repro values (seeding strips the baked-in postcode; the postcode-only round trip re-serialises
`*_address` without the old postcode; column-wins on disagreement; website-sync and
postcode-only shapes). Verified 5/6 fail against the old raw-`line1` seeding and 6/6 pass
with the fix. All four gates green (lint 0 errors, tsc, vitest 3472 passed, build).

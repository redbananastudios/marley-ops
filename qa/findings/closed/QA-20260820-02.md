## Summary
The dashboard's "Awaiting deposit" tile and /bookings' "£100 outstanding" queue answer the same question with different definitions — on staging right now they simultaneously show **1** and **6** — even though the dashboard code's own comment claims it "mirrors /bookings".

## Repro
1. Admin login on staging (2026-08-20, build 438dcb5). Open `/` — needs-action tile "Awaiting deposit" shows **1**.
2. Open `/bookings` — the "£100 outstanding" deposit queue shows **6 jobs / £600** (E2E-SENT-001, E2E-DEP-001, E2E-CREW-001/002/003, QA-SENT-20260820-1).
3. Both numbers faithfully render their own SQL — the definitions differ:
   - Dashboard: `awaitingDeposit: statusCounts.get("provisional") ?? 0` — counts **leads with status='provisional'** (`app/(dashboard)/page.tsx:374`), 1 on staging.
   - /bookings: accepted, uncancelled quotes with `deposit_paid_at` null (`lib/bookings/load-signals.ts` + `classifyBooking` → `deposit_outstanding`), 6 on staging — five of those leads are status 'confirmed' with unpaid deposits.

## Evidence
- `app/(dashboard)/page.tsx:370-374` — comment literally says "Money pipeline (mirrors /bookings): provisional = accepted awaiting the deposit", then counts `leads.status='provisional'`.
- Service-role SQL 2026-08-20: `leads where status='provisional'` → 1 row; accepted uncancelled quotes with `deposit_paid_at is null` → 6 rows (the /bookings queue's own definition, reimplemented and matching its render exactly).
- Screenshots: run artifacts `shot-dashboard.png`, `shot-bookings.png`.

## Suspected cause
A lead can be `confirmed` (or otherwise past `provisional`) while its accepted quote's deposit is still unpaid — the tile's status proxy diverges from the money truth the /bookings queue computes. On prod the accept flow usually moves status and deposit together, so the two agree by coincidence, not by construction; any hand-confirmed lead with an unpaid deposit splits them silently.

## Suggested fix (repair agent)
Derive the tile from the same signal /bookings uses (count of `deposit_outstanding` bucket rows / accepted uncancelled quotes with `deposit_paid_at` null), or rename the tile if the product intent really is "provisional leads". Display-count only — no money movement involved.

## Verify
Seed (or find) a lead with status `confirmed`, an accepted quote, and `deposit_paid_at` null; confirm the dashboard tile and the /bookings deposit queue report the same count for the same state.

## Fix

Branch `qa-repair/QA-20260820-02` (first-pass, 2026-08-20).

Both dashboard money tiles now count off the SAME classified ledger /bookings and the /payments Due tab render, instead of two different proxies:

- `app/(dashboard)/page.tsx` — the ~70-line inline balance-due IIFE (which re-implemented `classifyBooking`'s inputs by hand, filtered leads to `status='confirmed'`, and silently capped at PostgREST's 1000-row limit because it never paginated) is replaced by one `loadBookingRows(supabase)` call. `awaitingDeposit` is now the count of `bucket === "deposit_outstanding"` rows — exactly the rows the /bookings "£100 outstanding" queue renders — instead of `statusCounts.get("provisional")`.
- `lib/bookings/queue.ts` — new pure `moneyTileCounts(rows)` helper next to the bucket classifier: `awaitingDeposit` = deposit_outstanding rows, `balanceDue` = balance_due + balance_overdue rows.

Why it's safe: display-count only — no money movement, no writes, no comms. `lib/bookings/load-signals.ts` was extracted (2026-08-16) precisely so surfaces share one ledger and "can never drift on what a booking owes"; the dashboard becomes its third consumer. `balanceDue` keeps its meaning (balance_due + balance_overdue buckets) but now matches /bookings exactly — the old confirmed-leads-only filter could undercount vs the queue the tile links to, and the tile's own doc comment already claimed it "mirrors /bookings".

Test: `tests/lib/dashboard-money-tiles.test.ts` — unit coverage for `moneyTileCounts` (including the exact divergence shape: deposit-unpaid bookings past 'provisional' status, with a diary entry) plus a source contract asserting `awaitingDeposit` never reads `statusCounts` and the page consumes `loadBookingRows` + `moneyTileCounts`. Verified to fail against the pre-fix page source (2 failures) and pass after. Gates: lint 0 errors · tsc 0 · vitest 1694 passed · build green.

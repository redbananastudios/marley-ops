## Summary
A first-login user's guided tour auto-starts 1.2s after page mount and can land its full-viewport click-blocking overlay directly on top of an already-open dialog, silently swallowing every click on the dialog's primary action button — and if the user instead presses Escape to dismiss the tour, that single keypress ALSO closes the dialog underneath it (both listen globally for Escape), losing whatever the user was doing with no error shown either way.

## Repro
1. Fresh estimator login (first login — the tour's `localStorage` "seen" flag absent). Navigate to `https://staging.ops.marleymoves.co.uk/schedule/surveys?leadId=<a real lead id>` so the "Book survey" dialog opens immediately on load.
2. Fill the dialog's start-time field.
3. Wait past the ~1.2s mark (or just take slightly longer than 1.2s to reach for the "Book" button, which is a completely normal human interaction speed) and click **Book**.
4. Expected: the survey is booked.
5. Actual: the click is silently swallowed — Chromium/Playwright reports the click target intercepted by `<path class="driver-overlay driver-overlay-animated">`, the tour's full-screen SVG overlay, which has rendered on top of the dialog with no interaction ever completing. No error is shown to the user; the dialog just doesn't respond.
6. Separately: if the user presses **Escape** to dismiss the tour instead, driver.js's own global `window.addEventListener("keyup", ...)` Escape handler destroys the tour — but the same keypress also triggers the survey dialog's own (Radix) `onEscapeKeyDown`, closing IT too. `components/schedule/scheduler-view.tsx`'s `closeCreateDialog(false)` even strips `?leadId=` from the URL on close, so the user lands back on a bare `/schedule/surveys` with no dialog and no obvious indication the booking attempt was abandoned.

## Evidence
- Tour auto-start timing, confirmed by source: `components/onboarding/tour.tsx:169` — `timer = setTimeout(run, 1200);` (fires ~1.2s after mount on first login).
- An `"estimator"` tour genuinely exists and targets this nav: `components/onboarding/tours.ts:19` (`TourName = "office" | "estimator" | "crew"`), with a step referencing "Book the free home survey straight from the lead" (line ~59).
- The tour overlay is a real full-viewport click-blocker, not merely visual: driver.js's overlay element (`node_modules/driver.js/dist/driver.js.mjs`) is an SVG with `style.pointerEvents="auto"` covering the full viewport, only punching through at the highlighted step's rectangle — the survey dialog is not the tour's highlighted target, so it is fully covered.
- The Escape collision is real and global-scope, not per-component: driver.js registers `window.addEventListener("keyup", ...)` (`node_modules/driver.js/dist/driver.js.mjs`, the `d()` function wired in `driver.js.mjs`'s init path) which emits `escapePress` → destroys the tour whenever `allowKeyboardControl` is enabled (the default) — with no check for whether a shadcn/Radix dialog is also currently listening for the same keypress.
- Directly reproduced live against deployed staging this run (role-agent evidence, run suffix `d357c3`): a Playwright click on **Book** timed out after ~80 retries with Chromium's own message identifying the intercepting element as `driver-overlay`; a follow-up attempt using Escape to dismiss the tour resulted in `page.url()` returning to `https://staging.ops.marleymoves.co.uk/schedule/surveys` with the `leadId` query param gone and the dialog closed, no booking created.

## Suspected cause
The tour's autostart in `components/onboarding/tour.tsx` (the `setTimeout(run, 1200)` at line 169) does not check whether another dialog/modal is already open before launching, and driver.js's own Escape handling (`allowKeyboardControl`, default on) is not scoped away from a Radix `Dialog`'s own `onEscapeKeyDown`/overlay stacking. A fix should either (a) suppress or defer the tour's autostart while any `[role="dialog"]` is already open on the page, and/or (b) disable driver.js's built-in keyboard handling (`allowKeyboardControl: false`) and let host-page dialogs own Escape, so the tour never silently competes with — or blocks clicks on — page content the user is actively using.

## Verify
Automate: open a survey (or any first-run) dialog on a role/page whose tour has `autoStart` enabled, wait past 1.2s without interacting, then click the dialog's primary action button — it must succeed (the click must not be intercepted by a `driver-overlay` element), and pressing Escape while the tour is visible must not also close an unrelated dialog opened before the tour started.

## Fix
Both halves of the suspected cause, smallest form:

1. **Auto-start now defers while a dialog is open.** New `components/onboarding/dialog-guard.ts` exports `hasOpenBlockingDialog()` — true when a *visible* `[role="dialog"]`/`[role="alertdialog"]` is mounted (Radix unmounts on close), excluding driver.js's own popover (which is also `role="dialog"`) and hidden shells (same `getClientRects()` visibility test the tour already uses for steps, so a display:none node can't suppress the tour forever). `tour.tsx`'s auto-start timer re-checks every 1.2s until the dialog closes, then runs; the timer is cleared on unmount as before. The manual "Take the tour" path (`mm:start-tour`) is untouched — an explicit request still runs immediately.
2. **`allowKeyboardControl: false`** in the driver config — driver.js's Escape listener is window-global, so one keypress closed both the tour and the dialog underneath (and `closeCreateDialog(false)` then stripped `?leadId=`). Tour control now lives entirely in the popover buttons (Next/Back/Done, ✕ via `allowClose`, "Don't show again"); the deliberate cost is losing arrow-key step navigation.

Safe: pure client-side tour code, no payments/comms/auth/schema surface, no behaviour change for users with no dialog open (single 1.2s timer fires and the guard returns false).

Test: `tests/components/onboarding/tour-dialog-guard.test.ts` — behavioural coverage of the guard (open/none/hidden/driver-popover/mixed) plus source assertions pinning `tour.tsx` to `allowKeyboardControl: false` and to consulting the guard (repo precedent: `tests/config/workflow-timeouts.test.ts`). The two wiring assertions were run against the pre-fix `tour.tsx` and fail there; full gates green after (lint 0 errors, tsc, 1904 vitest, build).

## Summary
The customer-facing cubic-survey self-fill page (`/cv/<token>`) has no photo-upload control at all — a customer can list items and write notes, but cannot attach a single photo — even though the admin's own cubic review UI for the exact same survey shows a working "Survey photos" upload widget, and the intended handoff ("customer submits `/cv` survey → admin reviews it, media playable") explicitly expects a photo to exist for the admin to review.

## Repro
1. No login needed. Seed (or use) a `cubic_surveys` row with a `share_token`, e.g. via the service-role client:
   ```js
   await sb.from('cubic_surveys').insert({ lead_id, client_id, share_token: '<token>', status: 'draft' });
   ```
2. Visit `https://staging.ops.marleymoves.co.uk/cv/<token>` as a customer would.
3. Add at least one item, scroll to the bottom of the page.
4. Expected: some affordance to attach a photo of the item(s) — a file input, camera capture, or drag-drop target — matching the "Survey photos" widget office staff see on the equivalent admin review page for the same survey.
5. Actual: only a customer-notes textarea appears. A full HTML dump of the `/cv/<token>` page contains zero `<input type="file">` elements and zero references to the `SurveyPhotos` component anywhere in the DOM.

## Evidence
`components/cubic/cubic-builder.tsx` line 741 renders `<SurveyPhotos>` only when `office && leadId` is true:
```tsx
{office && leadId ? (
  <SurveyPhotos ... />
) : null}
```
`app/cv/[token]/page.tsx` invokes `<CubicBuilder mode="customer" .../>` and never passes a `leadId` prop, so `office` is false and `leadId` is undefined for every customer-mode render — the photo widget can never mount on this route, regardless of the survey's actual state. Confirmed live: fetched the full rendered HTML of a real `/cv/<token>` page (marker survey, share_token `qa-sentinel-cv-jxi197`) and grepped it — 0 matches for `type="file"` or `SurveyPhotos`. The admin review page for the same survey (`/leads/<id>/cubic`) does render the widget (screenshot confirms an empty "Survey photos" upload area present).

## Suspected cause
`components/cubic/cubic-builder.tsx:741` (the `office && leadId` gate) — `app/cv/[token]/page.tsx` never supplies `leadId` in customer mode, so the gate is unconditionally false on this route. The underlying photo-storage pipeline (bucket + `job_media`/survey-photo table) already works for office mode and looks reusable for customer mode; the repair agent should verify independently which prop/condition is the actual blocker before changing the gate.

## Verify
On `/cv/<token>` for a fresh marker cubic survey (no `leadId` involved), a photo-upload control must be present and usable: the customer can select/capture a file, it uploads, and afterward a service-role read-back of the survey's photo-storage table shows a row whose referenced storage object actually exists in the bucket (non-zero bytes). The admin review page for the same survey must then show that same photo as loadable (non-zero bytes, correct content-type), not just a stored path.

## Triage (2026-08-28) - stays OPEN, and it is not a safe-fix

Confirmed still real. `CubicBuilder` gates the photo widget on
`office && leadId`, and `/cv/[token]` renders it with `mode="customer"` and no
`leadId` - indeed `CubicBuilderProps` has no `token` or `leadId` field at all,
so the gate is unconditionally false on that route.

**Flipping the gate would not work**, which is why this is misclassified as
safe-fix. Every server action the photo widget calls is gated by
`requireOfficeProfile()`, and a `/cv/<token>` visitor has no office session. The
render gate is not the only blocker; the whole action layer assumes a logged-in
office user.

**What already exists and is reusable:**

- The token-as-credential write pattern is solved in `app/cv/[token]/actions.ts`
  (`submitCubicCustomerAction`): service-role client, re-validates `share_token`
  on every write. A customer photo action should copy that, not the office one.
- The storage seam (`lib/storage/media-store.ts`, `tus-upload.ts`) and the
  bucket/path scheme (`lib/survey-photos.ts`) are provider-agnostic and reusable
  as-is.
- `survey_photos.uploaded_by` is nullable, so a customer upload is not blocked
  by schema.

**What does not port:**

- `createSurveyPhotoUploadTargetAction` mints the target using the office user's
  session access token; a customer flow has none, so it needs a service-role
  variant - the same shift the DB write side already made.
- `survey_photos.survey_id` references `surveys`, NOT `cubic_surveys`, so a
  customer action needs its own token-scoped find-or-create for the `surveys`
  row.

**Size: roughly half a day**, small-to-medium feature. Reclassify as a build
item rather than leaving it in the repair queue, where its class label promises
a fix the queue cannot deliver.

## Implemented, NOT closed (2026-09-02, PR #214)

The customer photo path is built and merged: a token-authenticated upload with a
JPEG/PNG byte sniff, size and per-survey count ceilings enforced in the database
(migration 0117's `add_customer_survey_photo`), server-generated object keys, the
share token re-validated on every call, and a per-lead advisory-locked
find-or-create for the `surveys` row the triage identified as missing. The office
review page reads the same rows, which is what this finding asked for.

**It stays OPEN because its own Verify clause has not been executed.** That clause
requires a live check — a control present and usable on `/cv/<token>`, the object
readable back from the bucket at non-zero bytes, and the same photo loadable on the
admin review page. None of that was done: the implementation is covered by unit
tests and four gates, not by a browser. Per the standing rule after four
audit-written specs broke on first run, an unexercised path is unverified.

To close it, run the Verify clause above against staging and record the artefacts.

Two things found while building it, both fixed in the same PR, neither part of the
original finding: `cubic-builder.tsx` rendered "Send to Marley Moves" and the
default brand's phone to EVERY brand's customer on this page, and accepting WebP or
HEIC here would have made the crew day sheet fail to render for every job on that
day (`job-sheet-load` labels every non-.png object image/jpeg and the dispatcher
swallowed the throw).

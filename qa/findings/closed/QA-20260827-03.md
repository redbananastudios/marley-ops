## Summary
Clicking "Create Quote" on a survey visit for a lead that has never had a quote before renders the generic error boundary ("Something went wrong loading this page") instead of opening the quote builder — even though the draft quote is actually created successfully underneath. A hard reload of the exact same URL, or navigating to `/quotes/{id}` directly, shows the draft is there and fine; only the client-side transition crashes.

## Repro
1. Role: estimator (staging), marker login. Precondition: a lead that has never had a quote, with a scheduled survey appointment assigned to this estimator.
2. Go to `/schedule/surveys`, open the appointment's view dialog, click **"Create Quote"** (`components/schedule/appointment-view-dialog.tsx:210` does `router.push('/quotes/new?leadId=' + lead.id)` — a client-side transition, not a full navigation).
3. Expected: lands in the quote builder at `/quotes/{new draft id}` pre-filled from the survey/lead.
4. Actual: the page renders the generic Next.js error boundary — "Something went wrong loading this page … quote <digest>." Console shows `Error: An error occurred in the Server Components render… digest <N>`.
5. Reproduced twice this run for two separate fresh leads (different digests each time — not a fixed digest).
6. Despite the crash, `app/(dashboard)/quotes/new/page.tsx` did its job: the appointment flips to `status='completed'`, `surveys.status='completed'`, and a new draft quote row exists (`quotes.status='draft'`, correct `lead_id`/`estimator_id`). A subsequent hard `page.goto()` of the identical `/quotes/new?leadId=…` URL, or a direct `page.goto('/quotes/{id}')`, loads the same draft with no error — so the underlying `createDraftQuote()` write path (`app/(dashboard)/quotes/actions.ts:78`) is not the broken part; only the client-side-transition redirect delivery is.

## Evidence
Live repro this run (estimator role agent, marker leads `ebe83a4c-…` and `015ff700-…`):
- First lead: crash on the `router.push` transition; SQL read-back after showed `quotes` row `MMR143` already existed (`status='draft'`, `lead_id=ebe83a4c-…`) and `appointments.status='completed'` for that lead's survey — the write had already committed despite the error screen.
- Second lead: same crash, same pattern — draft `MMR146` created, appointment completed, error screen shown regardless.
- In both cases a follow-up direct load of `/quotes/{id}` rendered the builder correctly with the seeded fields intact (customer name/phone/addresses from the lead).

## Suspected cause
`app/(dashboard)/quotes/new/page.tsx:33-37` calls `createDraftQuote({ leadId })` then `redirect(...)` during the page's server render. `app/(dashboard)/quotes/actions.ts` already documents (lines ~206-211) that Next can invoke this render twice for one navigation and handles the resulting duplicate-insert race at the DB level (`quotes_one_draft_per_lead_uq`) — but that comment only covers the SQL race, not what happens to the `redirect()` call on whichever of the two render passes loses/duplicates. The crash is specific to `router.push` (client-side RSC transition) from `components/schedule/appointment-view-dialog.tsx:210`; a full `page.goto()` of the same URL never crashes, which points at the interaction between the double-render and how the redirect result is delivered back to the client-side transition specifically (as opposed to a full document navigation).

## Verify
From a fresh marker lead with no prior quote and a completed survey appointment assigned to the estimator, click "Create Quote" in the survey view-dialog (a `router.push` client transition, not a full page load). The quote builder must open directly with no error boundary, and the draft quote it shows must be the only draft row created for that lead (no duplicate `quotes` rows, confirmed by SQL count = 1).

## Resolution (2026-08-28, branch `qa/ui-safe-fixes`)

Confirmed still real. The root cause is NOT the redirect-swallowed-by-try/catch
trap: `app/(dashboard)/quotes/new/page.tsx` is a plain Server Component page
with no try/catch anywhere near the `redirect()`.

It is a **write during a render Next can invoke more than once for one
client-side navigation**, and the codebase already knew: `createDraftQuote`
carries the comment *"/quotes/new creates the draft during its render, which
Next can fire twice for one navigation, and both passes clear the resume check
above before either commits"*. The DB race is handled - a partial unique index
plus re-read-the-winner, so both passes return ok. Nothing handled the TWO
`redirect()` throws that come with it. A hard load is a single render pass and
a clean 307, which is why reloading the identical URL always worked.

**Fixed** at the reproduced call site by calling `createDraftQuote` directly
from the client handler - one deterministic invocation - and pushing straight
to the resulting id. This mirrors the pattern already used for the analogous
race in `createLeadAndOpenAction` / `createQuoteWithLeadAndOpenAction`.

## The wider hazard, raised separately as QA-20260828-01

Seven other call sites reach the same page through `<Link prefetch={false}>`.
The crash is in the shared page render, not in `router.push`, so they are
exposed to the same class of failure on a client-side click. Corroborating
evidence: `e2e/estimator/work-quote.spec.ts` already wraps that exact `<Link>`
click in a 3-attempt retry loop with no comment explaining why, which reads
like a prior workaround for this same crash rather than ordinary flake-proofing
(and it is currently skipped for a missing password, so it provides no cover
either way). Fixing that properly means making `/quotes/new` not write during
render, which changes seven entry points and three e2e specs - deliberately out
of scope for a minimal fix to the reported finding.

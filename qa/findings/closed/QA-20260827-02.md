## Summary
The read-only "view appointment" dialog opened from `/schedule` shows the wrong clock time in its header whenever the viewer's machine isn't set to UK time — the office's own confirmed booking time renders off by the local/UTC offset — because this one formatter is missing the `Europe/London` timezone that every sibling schedule component passes.

## Repro
1. Role: admin (staging), any login. Precondition: an appointment with `starts_at` in UTC, e.g. `2026-08-28T09:00:00+00:00` (09:00 UTC = 10:00 BST).
2. Go to `https://staging.ops.marleymoves.co.uk/schedule?date=<that day>`.
3. The day-panel card (rendered by `components/schedule/schedule-allocation-view.tsx`, which explicitly passes `timeZone: "Europe/London"`) correctly shows **"10:00–15:00"**.
4. Click the card to open the view dialog (`components/schedule/appointment-view-dialog.tsx`). The header shows **"Friday 28 August · 09:00"** — one hour off from the card that opened it, and off from the real UK-local booking time.
5. Expected: header time matches the day-panel card and the actual UK-local `starts_at` (10:00). Actual: header shows the raw UTC hour (09:00) because the browser running the test was on a UTC clock; on any browser set to a non-UK timezone the header would be off by that browser's offset instead — it only ever renders correctly by coincidence, when the viewer's machine happens to be on UK local time.

## Evidence
`components/schedule/appointment-view-dialog.tsx:144`:
```ts
? `${when.toLocaleDateString("en-GB", { weekday: "long", day: "numeric", month: "long" })} · ${when.toLocaleTimeString("en-GB", { hour: "2-digit", minute: "2-digit" })}`
```
No `timeZone: "Europe/London"` option is passed to either call, so both fall back to the JS runtime/browser's local zone. Compare the same file's sibling components, both of which force UK time explicitly:
- `components/schedule/schedule-allocation-view.tsx` (~line 145): `toLocaleTimeString(..., { timeZone: "Europe/London" })`
- `components/schedule/reschedule-dialog.tsx` (~line 148): same pattern, `timeZone: "Europe/London"` included.

Live repro this run (marker run `x7f2q9`, admin role agent, real appointment "E2E Crew Job Customer", `starts_at=2026-08-28T09:00:00+00:00`): day-panel card = "10:00–15:00" (correct BST), view-dialog header = "· 09:00" (raw UTC, wrong by exactly the UK DST offset) — same underlying row, same page load, two components disagreeing on the clock.

## Suspected cause
`components/schedule/appointment-view-dialog.tsx:144` — add `timeZone: "Europe/London"` to both the `toLocaleDateString` and `toLocaleTimeString` calls, matching `schedule-allocation-view.tsx` and `reschedule-dialog.tsx`.

## Verify
Seed (or use) an appointment with a known UTC `starts_at` that differs from its UK-local wall-clock time (i.e. during BST). Open `/schedule?date=<day>`, confirm the day-panel card's time. Open the view dialog for the same appointment; its header time must match the day-panel card exactly (both reflecting `Europe/London`), regardless of the test runner's own system timezone.

## Resolution (2026-08-28, branch `qa/ui-safe-fixes`)

Confirmed still real. Neither `toLocaleDateString` nor `toLocaleTimeString` in
the dialog header passed a `timeZone`, so both took the VIEWER's zone.

**Correction to this finding's evidence:** it cites
`components/schedule/reschedule-dialog.tsx` as a correct sibling. That file
passes no `timeZone` either. The real correct sibling is
`components/schedule/schedule-allocation-view.tsx`, which is the day-panel card
the dialog is opened from - which is exactly why the two disagreed on screen.

**Fixed** with `UK_TZ` from `lib/uk-time.ts` rather than an inline literal.
The one correct sibling inlines the string, but `uk-time.ts`'s own docstring
says render-time date text must pin `UK_TZ`, so the constant is canonical and
the literal is the thing that drifted.

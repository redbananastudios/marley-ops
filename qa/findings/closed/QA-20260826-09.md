## Summary
Two independent credential-hygiene holes in the same function pair. Every other misconfiguration on this path fails closed and loudly (unset → 401, unknown slug → FK error → 5xx); these two fail OPEN and silent, and the consequence of the first is a wrong-brand financial document.

**(a) Duplicate secret → silent misattribution.** `resolveIngestBrand` returns the FIRST secret that matches, and Marley is always first in the list. Two brands configured with the same secret value silently file the second brand's enquiries under Marley. Nothing validates that configured secrets differ.

**(b) The `LEAD_INGEST_SECRET_` prefix scan has no allowlist.** Any env var starting with that prefix becomes an accepted credential for a brand named after its suffix, with no check against the brands table.

## Repro
(a):
1. An operator wiring `app.env` copies the existing `LEAD_INGEST_SECRET` value into `LEAD_INGEST_SECRET_PITMANS` instead of generating a new one.
2. Expected: refused at config time, or at minimum the brand resolves correctly.
3. Actual: every Pitmans push presents that token; the loop tests Marley first, `ingestAuthorized` returns true, `resolveIngestBrand` returns `"marley"`. The lead inserts with `brand: 'marley'` — a valid FK, so nothing errors and nothing logs. `payloadBrandMismatch` never trips because the plugin sends no `brand` field. Downstream: `next_quote_ref('R','marley')` mints MMR### instead of PMR###, the quote carries MarleyMoves Ltd's legal line, `card_payments_enabled` reads the wrong value, and the customer is emailed from hello@marleymoves.co.uk. Meanwhile the pull rail reconciles on `(brand='pitmans', external_lead_id)`, finds no row, and re-inserts the SAME enquiry under brand pitmans — a duplicate customer, because the brand-scoped index no longer collides.

(b):
1. Rotating the push secret the way `docs/ovh-deployment.md` describes invites parking the outgoing value as `LEAD_INGEST_SECRET_PITMANS_OLD`.
2. Actual: that name resolves to brand `pitmans_old`, which is ≥16 chars so it authenticates. `resolveIngestBrand` returns `pitmans_old`, the request passes the 401 gate, and `landWebsiteLead`'s insert violates `leads_brand_fkey` → 500. Loud and no lead is misattributed (the FK holds the line), but the outage is created purely by the naming convention having no allowlist. Same shape for a suffix naming the `group` pseudo-brand.

## Evidence
`lib/leads/ingest.ts:87-91` (the unguarded prefix scan) and `:109` (first-match-wins with Marley seeded first).

## Suspected cause
Both follow from deriving identity from the env var NAME without validating the resulting set. Cheap fixes, same fail-closed posture as the rest of the file: reject at `brandIngestSecrets` time when two configured secrets share a value (or when a per-brand secret equals `LEAD_INGEST_SECRET`), and filter the enumerated slugs against the brands table.

Filed `risky`: it is an auth path and (a) produces wrong-brand money documents.

## Resolution (2026-08-28, branch `qa/ingest-rail-cannot-lose`)

Confirmed still real, both holes.

**(a) Duplicate secret - the dangerous one.** Fixed by refusing, not by
ordering. A duplicate is a question with no answer: two brands presenting the
same token are indistinguishable, so first-match-wins does not resolve the
ambiguity, it hides it - and the first candidate is always the default brand,
so the quiet outcome was the other brand's customer filed under the default
one, carrying its quote-ref prefix, its legal line and its sending address onto
a document a real person receives.

`brandIngestSecrets` now drops every entry whose value is shared, and
`sharedIngestSecretBrands` names them so the refusal is reportable rather than
silent - otherwise an operator who pasted one value into two variables sees
401s and debugs the secret rather than the duplication.

Placeholder-short values are exempt: they authenticate nothing already, and
counting them would let two blank placeholders collide and disable a brand that
was never configured.

**(b) No allowlist.** The route now resolves the slug against `brands` and
answers 401 for one that names no row, instead of letting it reach the insert
and die on the foreign key as a 5xx. The existing docstring argued that 5xx was
acceptable because nothing is misfiled, which is true - but it is an outage the
naming convention manufactured, with a diagnostic pointing at the database
rather than at the environment variable. The `group` pseudo-brand is refused
with it: it owns no website and mints no refs.

An unreadable `brands` table is a **500, never a 401** - a real enquiry must get
the answer that means retry, not the one that means you are not welcome.
Deliberately a direct query rather than `getBrand()`, which discards its error
and would render a database outage as an unknown brand.

Not filtered on `active`: an inactive brand row is a config state, not a reason
to turn away a live customer's enquiry.

## For Peter

Refusing a shared secret takes **every** brand presenting it offline, the live
default brand included. That is the intended trade rather than an oversight: a
401 fires the caller's documented office-email fallback and the enquiry still
reaches a human, whereas a misfiled lead reaches the wrong customer under the
wrong company's name. It only triggers on an actual misconfiguration.

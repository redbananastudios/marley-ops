## Summary
The removals diary's booking dialog can never book a bare client (a client with no lead), so the gate-11 brand picker that b4687f1/#96 wired into `AppointmentDialog` is unreachable dead code on `/schedule/removals` — the fix's own commit message says it closes the bare-client dead end on "the removals and surveys diaries", but only surveys actually offers bare clients in its combobox.

## Repro
1. Role: admin (staging). Precondition: a client row with NO leads (a "bare client").
2. Open `/schedule/removals`, click "New", search the lead combobox for the bare client's name.
3. Expected (matching `/schedule/surveys` and b4687f1's stated intent): the client appears as a "client — opens a new enquiry" option; selecting it renders the brand picker (`requireBrand`), booking creates lead + appointment with the chosen brand.
4. Actual: combobox shows "No matches" (verbatim DOM text) — the bare client is not offered at all, with or without the brand layer.

## Evidence
Live repro on staging 2026-08-26 (marker client `03b40c20-e288-4387-9a21-49fb37a252a7`, since cleaned up): removals "New" dialog search → "No matches". Control on the same run: `/schedule/surveys` offered a bare marker client, rendered the brand picker (`[data-testid="brand-picker"]`, options Marley/Pitmans), enforced "Choose which brand this enquiry is for." when unset, and a Pitmans booking wrote `leads.brand='pitmans'` + `appointments.brand='pitmans'` (SQL read-back exact).

Source (re-verified independently by the main loop on `8f9475b`):
- `app/(dashboard)/schedule/surveys/page.tsx:117-132` builds `clientOptions` from bare clients with `isClient: true` and line 161 passes `leads={[...leadOptions, ...clientOptions]}`.
- `app/(dashboard)/schedule/removals/page.tsx:88-112` builds `leadOptions` from the `leads` table only and passes `leads={leadOptions}` — no `clientOptions` merge exists in the file.
- `components/schedule/appointment-dialog.tsx:519`: `requireBrand = !isEdit && !!selectedLead?.isClient && brands.length > 1` — can only ever be true if an `isClient` option is selectable, which removals never supplies.

## Suspected cause
`app/(dashboard)/schedule/removals/page.tsx` was never given the bare-client `clientOptions` merge that `surveys/page.tsx` has. Fix shape: replicate the surveys pattern (query bare clients, map with `isClient: true`, spread into the `leads` prop). NOTE for the repair: b4687f1's commit message treats bare-client booking as intended on BOTH diaries, so this is filed safe-fix; if booking a removal for a client with no enquiry is actually NOT wanted product behaviour, close as wontfix with that ruling instead of changing code.

## Fix
`app/(dashboard)/schedule/removals/page.tsx` now replicates the surveys diary's bare-client pattern verbatim: `client_id` added to the leads select (needed to know which clients already have an enquiry), a bare-clients query (`merged_into_id is null`, `is_active`, minus clients with leads) mapped with `isClient: true`, and the result spread into the dialog's `leads` prop (`[...leadOptions, ...clientOptions]`). No dialog or server changes needed — `createAppointment`'s bare-client path (`!leadId && clientId` → brand validation → `ensureLeadForClient`) is already appt-type-agnostic, and the dialog already sends `clientId`/`brand` for removals; the options were simply never offered. The bare-clients query is a plain select (not `fetchAllRows`), matching surveys exactly and keeping the existing removals invariant test (exactly 2 `fetchAllRows` in the file) true.

Test: `tests/lib/schedule/diary-bare-client-parity.test.ts` — source-parity invariant in the repo's `release-reliability-invariants` idiom, asserting BOTH diaries query bare clients, mark them `isClient: true`, filter by `clientIdsWithLeads`, select `client_id`, and pass `[...leadOptions, ...clientOptions]`. Fails on the pre-fix removals source (verified via stash), passes after; surveys leg guards against the same regression there.

Safe because: read-only data plumbing on a page already shipping the multi-brand dialog — no schema, payments, comms, or auth surface touched; single-brand mode is unaffected (`requireBrand` still needs `brands.length > 1`, and the server ignores/defaults brand exactly as before).

## Summary
On a client's detail page, each quote in the Quotes card is labelled "`<status>` · `<date>`" — e.g. "Accepted · 21 Aug 2026" — but the date shown is the quote's **creation** date (`created_at`), not the date of the status it is labelled with. So "Accepted · 21 Aug" does not mean the quote was accepted on 21 Aug; it means it was *created* on 21 Aug. Any quote whose acceptance/decline happened on a different day from its creation displays a misleading date beside the status word.

## Repro
1. Admin login → `/clients/<clientId>` for a client with an accepted quote whose `accepted_at` differs from `created_at`.
2. Look at the Quotes card row: it reads "Accepted · `<created_at date>`".
3. Expected: the date should reflect the labelled status (when it was accepted), or the label should not imply the date is the status-change date. Actual: it always shows `created_at` regardless of status.

Concretely on staging (2026-08-21), fixture quote `QA-Rbbd43f-1`:
- `created_at = 2026-08-21T00:12Z`, `accepted_at = 2026-08-20T09:00Z`, `status = accepted`, `grand_total = 1200`.
- The card rendered "Accepted · 21 Aug 2026 · £1,200" — 21 Aug is `created_at`, not the 20 Aug the quote was accepted.
- (The fixture's `accepted_at` is one day before `created_at`, which surfaced the gap; in normal data acceptance is *after* creation, so a real quote accepted days after it was built would show the earlier creation date next to "Accepted", understating when it was accepted.)

## Evidence
Source, read 2026-08-21:
- `app/(dashboard)/clients/[id]/page.tsx:66` — the quotes query selects only `id, quote_ref, grand_total, status, created_at` (no `accepted_at`/`declined_at`/status-change timestamp).
- `app/(dashboard)/clients/[id]/page.tsx:243` — renders `{q.status} · {fmtDate(q.created_at)}` — the status word paired with `created_at`.

SQL confirming the mismatch (service role, staging):
```sql
select quote_ref, status, created_at, accepted_at, grand_total from quotes where id = '<fixture quoteId>';
-- status=accepted, created_at=2026-08-21T00:12Z, accepted_at=2026-08-20T09:00Z
```

## Suspected cause
Two-hats: the card labels the row with `status` but sources the date from `created_at`, so the label and the value describe different events. Fix options: select the status-appropriate timestamp (`accepted_at` when accepted, `declined_at`/etc. otherwise, falling back to `created_at`) and show it, or relabel the line so it clearly reads as the creation date (e.g. "Accepted · created 21 Aug").

## Verify
1. On `/clients/<clientId>` for a quote where `accepted_at` (or the relevant status timestamp) differs from `created_at`, assert the Quotes-card date matches the status the row is labelled with (not `created_at`), OR that the label no longer implies the date is the status-change date.

## Fix
First-pass repair, 2026-08-21, branch `qa-repair/QA-20260821-02`.

- New pure helper `lib/quote/status-date.ts` `quoteStatusDate()`: maps the status word to the timestamp of the event it names — `accepted` → `accepted_at`, `rejected` → `declined_at` (the column `rejectQuote` stamps), `sent` → `email_sent_at`; `superseded` records no supersede time (the retire is a bare status flip, see `lib/quote/supersede.ts`), so it shows its send date — the last event the row records; `draft` and any missing timestamp fall back to `created_at`, so no row ever loses its date.
- `app/(dashboard)/clients/[id]/page.tsx`: the quotes query now also selects `email_sent_at, accepted_at, declined_at`, and the card renders `{q.status} · {fmtDate(quoteStatusDate(q))}` instead of pairing the status with `created_at`.
- Safe: display-only — one read query widened by three columns, no writes, no schema, no comms. The finding's fixture (`created_at` 21 Aug, `accepted_at` 20 Aug) now renders "Accepted · 20 Aug 2026".
- Test: `tests/lib/quote/status-date.test.ts` (7 cases) — the first case is the finding's exact fixture and fails against the old behaviour (pairing with `created_at`); also covers rejected/sent/superseded, the fallbacks, and an unknown status.

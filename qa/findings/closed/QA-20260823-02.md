## Summary
The quote total shown to the office and put in the customer's emailed PDF at Send time is a live client-side recomputation from current pricing settings; the `quotes.subtotal`/`grand_total` columns that everything else in the app reads (quotes list, and critically `accept-flow.ts`'s deposit/invoice amount via `quote.agreed_price ?? quote.grand_total`) are only refreshed by a debounced autosave that never fires on page load — only on a subsequent field edit. Opening a draft and sending it without touching any field emails the customer a price the database, and everything downstream of the database, disagrees with.

## Repro
1. Admin login. Seed (service-role) a `quotes` row with `status:'draft'`, `subtotal`/`grand_total` set to a value that will NOT match what `computeQuote()` derives from the row's `state_blob`/`breakdown` under current `business_settings.pricing` (in practice this happens for real rows whenever pricing settings change after a draft was last saved).
2. Open `/quotes/<id>` — do not edit any field.
3. Click the "Step 7: Review & send" progress dot (no `values` change → no autosave fires).
4. The bottom bar "Quote total" / Send dialog "Total move cost" show the LIVE recomputed figure (this run: £890).
5. Click Send → confirm in the Send dialog. Toast: "Quote sent…".
6. `quotes.grand_total`/`subtotal` are UNCHANGED from step 1 (£900 in this run) — `setQuoteStatus(quoteId, "sent")` only flips status, never touches money columns.
7. The customer's PDF/email quoted £890; `quotes.grand_total` (what `accept-flow.ts` uses for the deposit/invoice amount at accept, since `agreed_price` is never set by send) says £900.

## Evidence
`app/(dashboard)/quotes/actions.ts:248-280` (`saveQuoteDraft`) — money columns are meant to always come from `computeQuote()`, but that's only called from the debounced autosave `useEffect` in `components/quote/quote-builder.tsx:151-171`, which explicitly skips its first render (`firstRender.current` guard) and is keyed only on `[values, quoteId, readOnly]` — not on `pricing`, which is fetched fresh server-side every page load (`app/(dashboard)/quotes/[id]/page.tsx:101`, `getPricingConfig(sb)`).

`components/quote/send-quote-dialog.tsx:168` — send only calls `setQuoteStatus`, never persists `breakdown.grandTotal`.

`lib/quote/accept-flow.ts:562,760,772,1401,1525,1958,2226` — every accept/invoice amount computation is `quote.agreed_price ?? Number(quote.grand_total ?? 0)`; `agreed_price` is never set by the send path, so `grand_total` is load-bearing for what the customer is actually charged.

SQL (this run, marker quote `QASENT-QB-A-1787487568658`, deleted after): before send `subtotal=grand_total=900`; wizard/Send-dialog/email all showed £890; after send `grand_total` still `900`, `email_sent=true`.

## Suspected cause
`components/quote/quote-builder.tsx:151`'s autosave effect should also fire on initial load (or the send path should persist `breakdown` before/at the moment it emails), and/or its dependency array should include `pricing`.

## Fix shipped (2026-08-23)

The send path now PERSISTS before it emails: `saveQuoteDraft(quoteId, values)`
runs first, recomputing server-side from the same `values` and writing every
money column, so what is emailed and what the database holds agree by
construction. `saveQuoteDraft` now returns its breakdown, and the dialog
refuses to send when the server's grand total differs from the figure on
screen — pricing settings moved since page load, and emailing then would send
a number the office never saw.

Deliberately NOT fixed by making the autosave fire on first render: that would
write to the database on every page open, including views the office only meant
to look at. Persisting at the moment of commitment is the narrower change.

A re-send is excluded — that quote's price is already what the customer holds,
and recomputing against today's settings would move it underneath them.
`saveQuoteDraft` additionally now REFUSES an accepted quote outright, because
accept-flow charges from `agreed_price ?? grand_total`; the guard is on the
server rather than on a client flag.

## Verify

## Summary
When an appointment's actual scheduled date (`appointments.starts_at`) has drifted from its accepted quote's `moving_date`, the crew job-detail page, the downloadable Job Sheet PDF, and the emailed/SMS'd crew day-sheet all show the STALE quote date instead of the real scheduled date — while the `/my-jobs` job LIST (a different code path) correctly shows the real date. A crew member reading their own job detail or day sheet could be told the wrong day for their own job.

## Repro
1. Any appointment with `appt_type='removal'` whose accepted quote's `moving_date` differs from the appointment's own `starts_at` (e.g. a reschedule where only the appointment was moved and the quote's `moving_date` wasn't rolled forward, or an iMVE/legacy import where the appointment date was firmed up on the appointment row only — both documented as real occurrences in this repo's history, e.g. the 2026-08-13 "Kong appt 16→17/08" panel fix).
2. This run reproduced it live on a QA-SENTINEL marker fixture: appointment `starts_at = 2026-08-23T09:00:00Z`, accepted quote `moving_date = 2026-09-05`.
3. Crew login, `/my-jobs` list for that appointment: shows **"SUNDAY 23 AUGUST"** — correct, computed from `appt.starts_at` (`app/my-jobs/page.tsx`).
4. Same crew login, `/my-jobs/[id]` detail for the SAME appointment: shows **"Saturday, 5 September 2026"** — the quote's stale date, not the real scheduled date.

## Evidence
`lib/job-sheet-data.ts:90`:
```ts
const moveDate = quote?.moving_date ?? (appt.starts_at ? appt.starts_at.slice(0, 10) : null);
```
This unconditionally prefers `quote.moving_date` whenever a quote exists, falling back to `appt.starts_at` only when there is no quote at all — backwards, since the appointment's `starts_at` is the actual scheduled diary slot (the thing crew and the office both edit when a date changes) and the quote's `moving_date` is the date agreed at quote time, which can go stale independently.

SQL proof (marker fixture, deleted after this run):
```
appointments.starts_at = 2026-08-23T09:00:00+00:00
quotes.moving_date     = 2026-09-05
```
`/my-jobs` list (`app/my-jobs/page.tsx`) groups purely by `appt.starts_at` → correctly showed 23 Aug.
`/my-jobs/[id]` (via `lib/job-sheet-load.ts` → `assembleJobSheetData`) → showed 5 Sept.

`assembleJobSheetData` is shared by three consumers, so all three are affected whenever a quote's `moving_date` and its appointment's `starts_at` diverge:
- `lib/job-sheet-load.ts` — the web job-detail view AND the downloadable Job Sheet PDF (`lib/job-sheet-docdef.ts:380`, rendered as the PDF's "hero" date).
- `lib/crew-sheet/daily-data.ts:71` — the emailed/SMS'd crew day-sheet's date field.

## Suspected cause
`lib/job-sheet-data.ts:90` — the fallback priority is inverted. `appt.starts_at` (the live diary slot) should be preferred over `quote.moving_date` (a point-in-time snapshot from quoting), not the other way round.

A regression test asserting `assembleJobSheetData({ starts_at: X, ... }, lead, { moving_date: Y, ... }, ...).moveDate === X` (with `X !== Y`) closes this.

## Fix

`lib/job-sheet-data.ts` — the precedence is inverted, so the appointment's own
`starts_at` (the live diary slot the office edits when a date changes) wins, and
`quote.moving_date` (a snapshot taken at quoting time) is the fallback for a job with
no dated appointment. All three consumers of `assembleJobSheetData` — the crew
job-detail view, the Job Sheet PDF and the emailed/SMS'd crew day-sheet — inherit it.

Not a bare `.slice(0, 10)`: that takes the **UTC** day, while `/my-jobs` buckets by
`Europe/London` (`app/my-jobs/page.tsx:162`). Through BST those disagree either side of
midnight, so the naive swap would have fixed the reported divergence and quietly
introduced a second one. New `ukCalendarDate()` in `lib/uk-time.ts` — the module whose
own docs say every server-side day boundary must go through it — returns the UK calendar
day, so detail, PDF, day-sheet and list now agree by construction.

**Why it's safe**: pure data assembly. No migration, no `lib/payments/**`, no
`lib/comms/**`, no auth/session code. `ukCalendarDate` is a new additive export that
changes no existing behaviour. Where the two dates already agree — every job except one
on live prod — the output is byte-identical.

**Second-order effect, deliberate and correct**: `moveDate` is part of the crew day-sheet
content hash (`lib/crew-sheet/daily-data.ts:71`), so a job whose dates diverge will hash
differently and re-send a superseding day sheet. That is the intended behaviour — crew
holding a sheet with the wrong day should be sent the right one. It fires only for
genuinely-affected jobs, not across the board.

**Test added**: four cases in `tests/lib/job-sheet.test.ts` — the audit's exact live repro
(appointment 23 Aug vs quote 5 Sept → 23 Aug), no-drift agreement, fallback when the
appointment has no date, and the BST midnight edge (23:30Z on 23 Aug → 24 Aug UK).
**Verified to fail 2/4 against the unfixed code** (the divergence and BST cases; the other
two are guard rails that must pass both before and after) and 21/21 pass after.

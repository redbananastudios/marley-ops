## Summary
Deleting a duplicate lead that has no sibling on its client fails outright ("Could not delete the lead.") whenever the lead has any `activities` or `communications` row — which is the common case for any real lead.

## Repro
1. Admin login (QA-SENTINEL admin user). Seed a client with exactly ONE lead, zero of the 8 `canDeleteLead` dependencies, and one `activities` row with `lead_id` = that lead.
2. `/leads/[id]` → Delete → Delete lead.
3. Expected: lead deleted, activity gone with it (per the action's own comment: "With no sibling, those rows go with the lead").
4. Actual: toast "Could not delete the lead."; the lead row and the activity row both still exist afterward.

## Evidence
SQL after the click: `leads` row present (id unchanged), `activities` row present with the same `lead_id`. Schema: `supabase/migrations/0001_init.sql` declares `activities.lead_id uuid references leads(id)` and `communications.lead_id uuid references leads(id)` with no `ON DELETE` clause (default NO ACTION/restrict) — unlike `follow_ups.lead_id`, which is `on delete cascade` (0014_follow_ups.sql). `deleteLeadAction` only re-points these three tables when there IS exactly one sibling; on the no-sibling path it does nothing to them before calling `leads.delete()`, so Postgres rejects the delete with an FK violation that the action's catch-all turns into "Could not delete the lead."

## Suspected cause
`app/(dashboard)/leads/actions.ts` `deleteLeadAction`, the `if (mergedInto)` block only runs the re-point/insert-merge-note steps; nothing analogous runs (delete or re-point) for `activities`/`communications` in the no-sibling branch.

## Why safe-fix
Display/write-path bug with a clear, narrow fix (e.g. delete the lead's own `activities`/`communications` rows in the no-sibling branch before deleting the lead; no money, auth, or schema change implied) — doesn't touch payment math, RLS, or comms sending.

## Verify
Re-run the repro above; assert the lead row and its `activities`/`communications` rows are all gone, and the toast reads a success message (e.g. "Lead deleted"), not "Could not delete the lead."

## Fix

`deleteLeadAction`'s no-sibling branch now deletes the lead's own `activities` and `communications` rows before deleting the lead (`app/(dashboard)/leads/actions.ts`). That is the behaviour the action's docstring already promised ("With no sibling, those rows go with the lead"); neither FK has an `ON DELETE` clause, so leaving them made Postgres refuse every real delete. `follow_ups` needs nothing — it cascades (0014). No schema change, no migration; the sibling merge path is untouched.

Safe because: the rows deleted are exactly this lead's own history, only after `canDeleteLead` has confirmed no quotes/money/diary/signatures exist, and only when there is no sibling to keep them on — the same rows Postgres would have cascaded had the FK been declared that way.

Test: `tests/lib/leads/delete-lead-history.test.ts` — fake DB enforces the real FK constraints (activities/communications restrict, follow_ups cascades). No-sibling case verified to FAIL pre-fix with the exact "Could not delete the lead." result from the repro; sibling re-point path covered as a regression guard.

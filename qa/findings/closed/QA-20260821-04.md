## Summary
Admin's "Return for changes" action on a submitted contractor statement reports success in the UI (success toast, dialog closes) but does not durably update the statement — it stays `status='submitted'` in the database, so the crew never actually receives it back as a draft to amend.

## Repro
1. This is CI's own permanent spec, not a manually driven repro: `e2e/office/contractor-pay.spec.ts` — "Office — Contractor pay (review a submitted invoice) › return a submitted invoice to the crew with a reason". CI's own seed (`scripts/seed-e2e.mjs`) creates a single `staff` row "E2E Pay Crew" with one `staff_statements` row (`ref=MMP-E2E01`, `status=submitted`).
2. Admin login (CI's `e2e-office@marleymoves.test`, role confirmed `admin` via live query) → `/finance/statements` → open the "E2E Pay Crew" row → Return → fill a reason → "Return for changes". No error toast is asserted by the test at this step, only that the flow completes.
3. Expected (the spec's own assertion): the row disappears from the default "submitted" filter — `getByText('E2E Pay Crew')` count 0 within 15s, because `returnStatementToCrewAction` sets `status='draft'`.
4. Actual: `getByText('E2E Pay Crew')` stays at count 1 for the full 15s window — the row never leaves "submitted".

Reproduced on **two independent CI runs**, 8 minutes apart, on two different commits with **no code changes to the statements action, the office view, or the spec between them**:
- push run [32447552408](https://github.com/redbananastudios/marley-ops/actions/runs/32447552408) on `bb76bc7e` (2026-08-21 04:36 UTC) — e2e job failed, same assertion.
- workflow_dispatch run [32448046368](https://github.com/redbananastudios/marley-ops/actions/runs/32448046368) on `ddd7479` (2026-08-21 04:45 UTC, the sha currently deployed to staging) — e2e job failed, identical assertion, identical locator/count.
- `git diff --stat 1f4a65f bb76bc7e` (last known-good run → first failing run) touches only `e2e/crew/invoicing-submit-lines.spec.ts`, `e2e/estimator/pay-statement.spec.ts`, docs/ledger files — **zero changes** to `app/(dashboard)/finance/statements/actions.ts`, `components/finance/office-statements-view.tsx`, or `e2e/office/contractor-pay.spec.ts` itself. The break is not explained by a code diff in this window.
- `test` job (lint/tsc/vitest) passed clean on both failing runs — this is an e2e-only, live-staging-only failure.

## Suspected cause
Not yet isolated to a line — `git diff` rules out the obvious files, so this needs the repair agent to check things a diff can't show: RLS policy behaviour on `staff_statements` UPDATE+`.select()` for the `admin` role specifically in the CI/staging environment (a policy that permits the UPDATE but not reading the row back in the same statement would make Supabase report `data: []` and the action would return `ok:false` "Only a submitted statement can be returned." even though the WHERE clause matched), or a session/cookie timing issue specific to the server action being called from a freshly-hydrated dialog in this CI environment. `app/(dashboard)/finance/statements/actions.ts:61-85` (`returnStatementToCrewAction`) and its RLS policy on `staff_statements` are the places to start.

## Verified

2026-08-21 (~12:20 UTC), against deployed staging (`f574d61`, `/api/version`
matched; the same sha CI run 32469569080 already reported green on).

**Root cause was a test bug, not a product defect.** Read `git show d678db8`
in full: `e2e/office/contractor-pay.spec.ts` originally located its "Return"
button with a page-wide, positional `getByRole("button", { name: "Return",
exact: true }).first()`. `/finance/statements` lists every contractor's
submitted invoice in "To pay" ordered by `period_start desc`; two sibling
specs (`e2e/crew/invoicing-submit-lines.spec.ts`,
`e2e/estimator/pay-statement.spec.ts`) each submit an invoice for the
*current* week, which always sorts above the seeded fixture MMP-E2E01's
*last*-week period — so `.first()` silently returned someone else's
invoice (proven in that commit's own evidence: the reason text landed on
the estimator's MMP009, while MMP-E2E01's `returned_at` stayed null).
`returnStatementToCrewAction` in
`app/(dashboard)/finance/statements/actions.ts:61-85` was always correct —
a clean `.eq('id', …).eq('status','submitted')` update-then-select, gated
by `requireAdmin()`, with no RLS or timing issue involved. The spec was
rewritten to scope every locator (row, Return button, dialog heading) to
the invoice's own seeded `ref`, guarded by `toHaveCount(1)` so ambiguity
goes red instead of silently acting on the wrong row. Confirmed the current
`e2e/office/contractor-pay.spec.ts` on disk carries that scoping (row
filtered `hasText: SEED.payCrew.statementRef`, dialog heading matched on
`Return ${ref} for changes`, Return button scoped to `row`).

**Independently re-confirmed the underlying product behaviour live**,
without running the CI spec itself (no `E2E_*` test-account credentials in
this environment for the `setup` auth project) — mirrored its steps with a
dedicated Playwright script + service-role seeding instead: minted a
throwaway admin user (`QA-SENTINEL Admin`, random password) and a marker
`staff` + `staff_statements` row (`ref=QA-SENTINEL-x7k2`, `status=submitted`,
`total=150`), all carrying `QA-SENTINEL`. Logged in as that admin, opened
`/finance/statements`, clicked **Return** scoped to the row matching that
ref (not `.first()`), filled a reason, submitted "Return for changes".

- UI: the row left the default "To pay" filter (count 0→ confirmed), then
  reappeared under "All" with a **Draft** pill.
- SQL read-back (service-role, same row id) after the UI action:
  ```
  status:        "draft"
  returned_at:   "2026-08-21T12:18:35.368+00:00"
  return_reason: "QA-SENTINEL verify: independent re-confirmation of d678db8 root-cause."
  ```

Both `returned_at` and `return_reason` populated, status flipped, row left
"submitted" — the exact assertion the spec makes, reproduced from scratch
against live staging today. Cleanup: all marker rows (staff,
staff_statements, profiles, auth user) deleted and re-verified gone by
targeted ID query; a handful of unrelated `QA-SENTINEL`-marked leads/
clients/profile/auth-user turned up in the broad sweep mid-run from a
concurrent session — left untouched per marker discipline (not created by
this run). Moving to `closed/`; class stays `risky` in the record for
historical accuracy (it was correctly triaged as risky-looking at file
time), but the finding is resolved and the underlying product code needs
no further action from Peter.

## Summary
A completed removal job stays on the crew's `/my-jobs` "Today" list looking exactly like an open job — no completed badge, no visual difference from a pending job (still shows the red MOVE tag, Job sheet PDF and Call customer buttons front and center).

## Repro
1. Role: crew (marker user `QA-SENTINEL Crew ...`).
2. Complete a `removal` appointment via the Complete Job dialog on `/my-jobs/[id]` (customer-absent path is fastest to reproduce).
3. Navigate back to `/my-jobs`.
4. Expected: some visual cue (completed badge / moved out of "Today" / greyed state) distinguishing it from jobs still to be done.
5. Actual: the job card is unchanged — same styling, same buttons, no indication the crew already signed it off.

## Evidence
`app/my-jobs/page.tsx` query: `.neq("status", "cancelled")` on `appointments`, with no filter or branch on `status === "completed"`, and the job card JSX has no completed-state rendering. Confirmed against SQL: `appointments.status = "completed"` for the reproduced job, yet the UI showed no change from before completion (screenshots taken pre/post).

## Suspected cause
`app/my-jobs/page.tsx` — the `jobs` query/mapping never carries `status` through to the card render, so there's no data available client-side to key a "Completed" badge off.

## Verify
Complete a job, reload `/my-jobs`, and assert the job card for that appointment renders a visually distinct completed state (badge/copy) rather than being indistinguishable from a pending job on the same day.

## Fix
As suspected: the page's `.select(...)` already asked for `appointments.status`, but the `Job` mapping dropped it, so the card render had nothing to branch on. The mapping now carries `status`, and the card's accent border / corner pill / title colour come from a new pure helper `lib/my-jobs/job-card.ts#jobCardLook(apptType, status)`: a completed job shows a green **Done** pill (`bg-success-bg text-success`, the same success tokens `/my-jobs/[id]`'s completed panel uses), a green left accent instead of the red/amber one, and a muted title — while the subtitle still names the visit type. Pending jobs render byte-identically to before (asserted in the test), and an unknown/null status renders as pending, never as done. Keying on `appointments.status` is right because both the crew sign-off (`app/actions/crew-signatures.ts` stamps `status: "completed"`) and the auto-complete cron set it; the card also covers office-side completions the crew never signed.

Safe because it's pure presentation on one crew page: no query shape change beyond reading a column already selected, no writes, no money/comms/auth surface.

Test: `tests/lib/my-jobs/job-card.test.ts` — unit tests on `jobCardLook` (completed ≠ pending for all three appt types, exact pre-fix pending pills preserved) plus a source contract that `/my-jobs` keeps `status` in the mapping and keys the card off the helper. Verified to fail pre-fix: the pre-fix page contains neither `status: a.status` nor `jobCardLook` (and the helper module doesn't exist), so both contract assertions and the imports fail against the old source.

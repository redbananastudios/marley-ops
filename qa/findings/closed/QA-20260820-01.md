## Summary
The staging CI's `e2e` job can hang indefinitely (observed: 3.5+ hours stuck on `npx playwright install --with-deps chromium`), and because no job in the workflow sets `timeout-minutes`, a hang holds the `deploy-staging` concurrency group for up to GitHub's 6-hour default — meaning the e2e safety net silently never reports on the deployed commit and every subsequent staging push queues behind the corpse.

## Repro
Observed live, run [32301326640](https://github.com/redbananastudios/marley-ops/actions/runs/32301326640) on commit `438dcb5` ("fix(csp): allow XHR/fetch to R2 in connect-src"):
1. `test` job: completed success 20:57–20:58 UTC (2026-08-19).
2. `deploy-staging` job: completed success 20:58–21:00 — the site went live on `438dcb5` (confirmed: `/api/version` returns `438dcb5`).
3. `e2e` job: step 5 `npx playwright install --with-deps chromium` started 21:00:47 and was STILL `in_progress` at 00:25 UTC 2026-08-20 (3h25m for a step that normally takes ~1 minute). Steps 6–8 (provision users, seed, Playwright suite) never ran.
4. Net effect: `438dcb5` — a CSP change specifically affecting **browser uploads** — deployed to staging with the e2e suite (the required check gating promotion to master) never executing, and nothing alerting anyone. A green deploy + absent e2e reads as "all good" unless someone opens the Actions tab.

## Evidence
- `actions_list list_workflow_jobs` for run 32301326640 (2026-08-20T00:25Z): jobs `test`=success, `deploy-staging`=success, `e2e`=`in_progress` with step `npx playwright install --with-deps chromium` `in_progress` since `2026-08-19T21:00:47Z`, steps 6+ `pending`.
- `.github/workflows/staging.yml`: no `timeout-minutes` on any of the three jobs (lines 20, 33, 81); `concurrency: { group: deploy-staging, cancel-in-progress: false }` (lines 15–17), so the wedged run blocks the group.
- Header comment (lines 3–6): "The `e2e` job is the required check that gates promotion of this commit to `master` (prod)" — i.e. the hung job is the prod-promotion gate itself.

## Suspected cause
`npx playwright install --with-deps chromium` downloads from GitHub-external CDNs with no timeout of its own; a stalled download hangs forever. The workflow adds no `timeout-minutes` backstop at job or step level, so GitHub's 6-hour default is the only kill. (One-off network stall is likely the trigger; the finding is the missing backstop, not the stall.)

## Suggested fix (repair agent)
Add `timeout-minutes` to all three jobs in `.github/workflows/staging.yml` (e.g. `test: 15`, `deploy-staging: 20`, `e2e: 45`) so a hang fails loudly within minutes instead of wedging the group for 6 hours. Optionally cache Playwright browsers (`~/.cache/ms-playwright` keyed on the @playwright/test version) so the flaky download step is usually a no-op. Same treatment is worth mirroring in `deploy.yml` (also has no timeouts). No app code involved.

## Fix

`timeout-minutes` set on every job in every workflow (2026-08-20, first-pass repair):
- `staging.yml`: `test: 15`, `deploy-staging: 20`, `e2e: 45` — a hang now fails the run within minutes instead of holding the `deploy-staging` concurrency group for GitHub's 6-hour default, and a killed `e2e` job is a visibly FAILED required check rather than a silently absent one.
- `deploy.yml` mirrored (`test: 15`, `deploy: 20`) — same non-cancelling concurrency-group shape. The `deploy` job's manual-approval wait doesn't count against the timeout; the clock starts when the job starts running.
- `qa-auto-merge.yml` (`gate: 20` — it runs all four gates including build, `merge: 10`) and `qa-findings.yml` (`raise: 10`) brought under the same rule so the test below can enforce it repo-wide.

Safe because the change is workflow metadata only — no app code, no behaviour change on any green run; timeouts only bite on a run that is already wedged. Values are ~3-10× the jobs' normal durations (test ≈4 min, e2e ≈15 min historically).

Test: `tests/config/workflow-timeouts.test.ts` — line-parses every `.github/workflows/*.yml` (repo has no YAML dep) and asserts each job under `jobs:` sets `timeout-minutes`. Verified to fail against the pre-fix workflows (names all 8 jobs) and pass after. A future workflow or job added without a timeout fails `npm test`.

Playwright browser caching (the finding's optional extra) deliberately not done — it changes what the e2e job installs and is not needed to make the failure scenario impossible; the timeout alone converts a stalled download from a 6-hour silent wedge into a fast loud failure.

## Verify
1. `.github/workflows/staging.yml` sets `timeout-minutes` on `test`, `deploy-staging`, and `e2e`.
2. The next staging push's run completes all three jobs (or fails within the configured timeout) — confirm via `actions_list list_workflow_runs` that no job sits `in_progress` past its timeout, and that the `e2e` job actually executed its Playwright step on the latest staging commit.

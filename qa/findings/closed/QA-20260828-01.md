## Summary
Signing in on staging with a correct email/password now takes ~26-28 seconds to actually land the user past `/login` — the Supabase auth call itself succeeds in under a second, but the client stays on `/login` showing "Signing in…" for that whole window because `router.push("/")` waits on the dashboard route's server render, which blocks on a chain of external calls. This is severe enough that it failed **every** authenticate-office/estimator/crew step in last night's full CI run, so the entire 178-test e2e suite (175 tests) never ran on the commit currently deployed to staging (`b653e0d`).

## Suspected cause
`app/(dashboard)/page.tsx:85-90` — `await syncSanityLeads(...)` blocks the whole render before `fetchExternalPanels()` (PostHog + Google Ads) is even kicked off, so their worst-case latencies stack instead of overlapping, and none of it is bounded by an overall page-level budget. The dashboard's own comment at line 44 already acknowledges these are "the slow leg... don't need per-click freshness" but only that leg is cached (5 min) — Sanity's incremental sync isn't, and isn't parallelised with it either. Every login funnels through this page (`router.push("/")` in `app/(auth)/login/page.tsx:28`), so any slowness here is universal, not feature-scoped.

## Resolution — closed 2026-08-28, fixed and verified green

Fixed in [#135](https://github.com/redbananastudios/marley-ops/pull/135) (`e6708e4`). The
symptom was real and the severity was right. **The stated cause was wrong**, and it is
recorded here because the next audit would otherwise re-derive it.

### Measured before → after (CI run 33156428938 against the deployed fix)

| role | before | after |
|---|---|---|
| authenticate office | ✘ 28.9s | ✓ 2.4s |
| authenticate estimator | ✘ 28.3s | ✓ 2.3s |
| authenticate crew | ✘ 28.5s | ✓ 2.3s |
| suite | 0 of 175 ran | **172 passed** |

### What the diagnosis got wrong

The finding blamed `await syncSanityLeads` blocking the dashboard render, and its `## Repro`
described the CI failures as the form never appearing. The Playwright traces from the failing
run itself (artifact `9666779783` of run `33121391706` — `test.trace` plus the browser's own
network log) refute both:

- **The form appeared and was used.** All three roles filled email + password and clicked
  "Sign in" on attempt 1, in 0.02–0.07s. The auth POST returned 200 in 393–657ms. `/login`
  serves in 4–8ms with `x-nextjs-cache: HIT` — it is statically prerendered and does no
  server work.
- **`syncSanityLeads` cannot be the cause on staging.** `SANITY_SYNC_DISABLED=true` in that
  container makes it a 0ms no-op, and estimator and crew are both redirected out of
  `app/(dashboard)/page.tsx` *above* the line that calls it — yet both still failed.
- **The `## Verify` assertion was unrunnable as written.** It required the CI `[setup]` steps
  to pass, but those failed for a reason downstream of the defect, so they could have gone
  green while the defect stood, or red while it was fixed.

### What it actually was

Three causes, none of them the one named:

1. **No `<Suspense>` boundary anywhere in `app/`**, so the client router could not commit the
   URL until the whole dashboard RSC payload had arrived *and* rendered — ~28 Supabase round
   trips plus 5.7s of client render, all on the login critical path.
2. **`router.refresh()` after `router.push("/")`** fired a *second* full render of the same
   route (2.37s / 3.29s / 6.65s), roughly doubling the wall clock for no benefit.
3. **Crew paid for a page it never sees** — the layout bounces crew to `/my-jobs`, but a
   layout and its page render concurrently, so the dashboard's entire read ran and was then
   discarded.

And the harness misnamed the failure it caught: `auth.setup.ts` retried by blindly re-driving
the form, but `login/page.tsx` never clears `loading` on success, so the button reads
"Signing in…" permanently and the retry waited 15s for a `Sign in` button that cannot exist.
That is where `locator.click: Timeout 15000ms exceeded` came from — and it reads as *"the
login page never rendered"*, which is what sent the audit to the wrong file. The loop now
distinguishes the two cases and names which one it hit.

### Still open, raised separately — do NOT treat these as closed by this finding

- **`lib/google-ads.ts:26` pins `API_VERSION = "v21"`, which Google has retired.** Verified
  directly: `v17`/`v19`/`v21` return HTTP 404, `v22`/`v23` return 401. `fetchAdSpend` has
  therefore returned `null` in ~30ms permanently, and the dashboard's ad-spend,
  cost-per-lead and ROAS tiles have been silently blank with nothing anywhere saying so.
- **`await syncSanityLeads` in the dashboard render is still a live defect on _prod_**, where
  the flag that neutralises it on staging is absent. Its backstop cron is daily
  (`0 6 * * *`); `wp-leads` runs `*/15`.
- **No request-duration logging.** `docker logs` held four lines for a ten-hour-old container,
  so a 30s render leaves no trace and the next occurrence is another guessing game.
- **Supabase latency is unbounded and occasionally awful.** Four estimator specs failed on
  attempt 1 of the verifying run with `page.goto` exceeding 30s, then all 172 passed on a
  re-run 7 minutes later. No Supabase call in the dashboard render has a timeout, and the
  box talks to hosted Supabase across the public network.

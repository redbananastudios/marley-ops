## DIAGNOSED (2026-09-02, main session — cause established, not a regression)

Neither hypothesis. The staging Zoho org has **exhausted its daily API call quota**, so
every call that touches invoices fails for the rest of the day while everything else
passes. Probed read-only against the staging org (20117092566) from `.env.e2e`:

```
TOKEN REFRESH        -> HTTP 200   scope=ZohoInvoice.fullaccess.all, access_token present
GET /invoice/v3/invoices -> HTTP 429
                        code=45 "The API call for this organisation has exceeded
                                 the maximum call rate limit of 1,000"
```

That explains every observation the audit recorded and nothing else does:

- **Only Zoho-touching specs fail.** Two of the four are literally named "…needs the
  Zoho staging org…". The other 182 specs pass.
- **They broke mid-morning, between two runs 4 minutes apart.** A quota is consumed
  progressively and trips at a threshold — it does not correlate with a diff. PR #205
  was simply the run in flight when the 1,000th call went out.
- **They persist across unrelated diffs** (`a2bf77b`, `b68575b`, `79f5a98` — a
  fixture-only change), because the quota is per-org per-day, not per-commit.
- The two days before this had ~32 PR merges, each triggering a staging e2e run that
  creates invoices. The cap was reached by our own CI volume.

**PR #205 is cleared** — there is no money regression in the ledger/matching changes.
The quota resets daily; re-running the workflow tomorrow should show all four green,
and that re-run is the confirmation step.

**But this uncovered a real defect, filed separately:** a Zoho 429 is not classified as
a lock-out (`isLedgerAccessDenied` matches only 401/403 — `lib/ledger/access.ts:60`), so
a sustained quota exhaustion raises **no integration-level alarm at all**. Every invoice
raise fails, each writing its own per-quote `zoho_*_error` and firing its own per-quote
failure email — precisely the "a per-entity alert for an integration-wide failure
destroys the signal" shape the 2026-08-27 lock-out decision exists to prevent. Prod runs
against the same 1,000/day cap on the live org. Note also that a token refresh returning
200 over a 429'd org is the same "a health probe must exercise the same scope as the
thing it certifies" trap that let the 2026-08-27 lock-out stay green.

| when | what | result |

**The window rolls at 00:00 in the org's own timezone — Europe/London — not UTC.**

UTC in winter.

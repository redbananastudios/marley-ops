## Summary
The pull rail has no cursor: every poll asks the plugin for the newest `WP_PULL_LIMIT` (200) rows of an unbounded, never-pruned table. Anything that falls behind that window is permanently unrecoverable by the only backstop — and because `failures` then reads 0, the standing reconcile issue **auto-resolves itself**, so the loss is erased rather than surfaced. The monitor clears the very evidence that would have shown the gap.

## Repro
1. Install the plugin on the brand's WordPress site BEFORE `LEAD_INGEST_SECRET_<BRAND>` is set on the Ops side — an order the docs explicitly sanction ("the route ships ahead of the plugin install"; "Until the pull env vars are set the job runs green but reports configured: false").
2. Every push 401s, so `pushed_at` stays NULL, while `syncWpLeads` returns `{ok:true, configured:false}` — a green run.
3. Accumulate more than 200 submissions.
4. Set the env vars. First poll requests `limit=200`; the plugin answers newest-first.
5. Expected: every unlanded submission eventually reconciles.
6. Actual: the oldest submissions are returned by no poll, then or ever after — each later window only moves forward. They are unreachable by the backstop, and the summary reads `inserted:200, failures:0`, then steady-state `failures:0`, i.e. clean.

## Evidence
- `lib/sync/wp-leads.ts` — the request carries only a fixed limit and a timestamp, no `since`/`after` cursor: `buildPullUrl(config.url, WP_PULL_LIMIT, ...)`.
- The plugin answers with no filter and no cursor (`plb_rest_submissions`): `SELECT ... FROM {$table} ORDER BY id DESC LIMIT %d`.
- `lib/sync/wp-leads.ts:334` — when `failures` is 0 it calls `resolveOperationalIssue(sb, WP_RECONCILE_ISSUE_KEY)`, contradicting its own contract two lines above: "a submission we have seen and cannot land is a customer waiting, so it must sit visibly open until it lands or a human deals with it."
- Second, independent instance of the same root cause: a submission that fails `websiteLeadIngestSchema` on every poll correctly raises the issue; once 200 newer submissions exist it leaves the window, `failures` becomes 0, and the record of an enquiry nobody ever answered is marked resolved by the monitor itself.
- The `WP_PULL_LIMIT` doc comment also misstates the invariant: with no cursor the bound is "more than 200 rows exist newer than the missed one", not "more than this arrive between two successful polls".

## Suspected cause
The rail was designed around a rate ("more than 200 between two polls is not a real number at a removals firm's volume") when the actual bound is a backlog. Fix: have the read endpoint accept `since_id` / `unpublished_only`, or persist the highest reconciled row id on the Ops side, so the window is anchored to what has actually been reconciled rather than to the newest row at poll time. Separately, `resolveOperationalIssue` must not fire merely because the unlandable row scrolled out of view.

Filed `risky`: silent customer-enquiry loss, and the fix spans the PHP plugin and the Ops rail. Not live yet (rail unconfigured), so the cheapest moment to fix it is before the plugin is installed.

## Resolution (2026-08-28, branch `qa/ingest-rail-cannot-lose`)

Confirmed still real, both halves. The signed query carried only `limit` and
`ts`; the plugin answered `ORDER BY id DESC LIMIT n` with no cursor and no
table total; and the resolve branch was gated on `failures > 0` alone, so a row
that had scrolled out of the window made `failures` read 0 and the standing
issue **resolved itself**.

The `WP_PULL_LIMIT` comment stated an invariant the code never provided - that
a lead only escapes recovery if more than 200 arrive between two polls. With
the window anchored to the NEWEST row the bound was a *backlog*, not a rate.

**A bigger limit would not have been a fix.** Two separate properties were
missing and both are now present:

1. **Loss is impossible** - the window is anchored to the first row we do NOT
   hold (`since_id`), and answers forward, oldest first. A row stays in view
   until it is accounted for.
2. **Loss is visible** - the endpoint now reports `total`, and the rail
   compares it against what it can account for. That comparison is over both
   whole tables, so a moving window cannot erase it.

The resolve is no longer gated on `failures` alone: `unaccounted > 0` holds it
open, and `unaccounted === null` (the endpoint reported no total) also holds it
open, because not being able to check is not the same answer as nothing being
wrong.

**The cursor is derived, never stored.** It is read from our own `leads` table
each poll. A stored cursor is state that can be lost or reset, and a lost
cursor skips rows in silence - the exact failure this rail exists to prevent.
An unreadable leads table is a FAILED run, never a poll from zero.

## Two things for Peter, neither blocking

**1. Breaking wire change, deliberately taken now.** The signature covers
`since_id`, so plugin and Ops must deploy together. That is only cheap because
the plugin is not installed anywhere yet (`/api/cron/wp-leads` reports
`configured:false`). Were it installed, an Ops-first deploy would 403 every
poll - loud, a failed run, no silent loss - but it must be one window.

**2. A hard-deleted `wp-` lead is re-landed.** The cursor derives from `leads`,
so deleting one rolls the window back below it. This is not new behaviour - the
old newest-200 window already resurrected any deleted lead whose plugin row was
still inside it, which for weeks it would be. What changes is reach: permanent
rather than expiring when the row falls out of the window. Closing it properly
needs a tombstone table consulted by both the cursor and the accounting, which
is new state and a migration. Flagged rather than assumed.

## A known, loud limitation

A permanently unlandable row pins the cursor beneath it, so rows past it are
only reachable while they fit in one page. That is deliberate: the alternative
is skipping the bad row, which is the silence this finding is about. It fails
LOUD - `unaccounted` counts the unreachable rows and holds the issue open until
a human clears the blockage. Documented on `contiguousReconciledUpTo`.

## Verify (updated)

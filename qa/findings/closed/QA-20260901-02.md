## Summary
On deployed staging, a customer accepting a quote via bank transfer at `/q/<token>` no longer flips the lead to `accepted`, no deposit/balance invoices are raised, and the pay screen stops rendering correct totals. This broke somewhere in the "/q accept-flow rewrite" that shipped as part of PRs #172-183 and was pushed to staging by QA run `cc42f50` (2026-09-01T16:33Z). That run's own `qa/LOG.md` entry is explicit that its customer-agent check covered only the **commercial** accept gate ("online accept categorically closed for commercial by design (gate 10b, confirmed by source read, not forced)") — the **residential/bank-transfer** path that is now failing was never exercised by that run, so its "0 findings" claim is accurate to what it tested, not a false-confident-narration case. But that same commit's own CI e2e run (against the live deployed staging site) failed the customer-accept P0 tests on the untested path, and every one of the three subsequent pushes to `staging` (`0f67cf0`, `5e0fbaa`, `82dac7a`, spanning 16:57Z–19:33Z) still fails the same tests. **This regression has now silently survived one QA push and three further repair-style pushes without anyone acting on the red CI it shipped with.**

Not a promotion risk to production right now: `origin/master` (deployed prod, sha `be31241`) does not contain any of these commits — confirmed via `git merge-base --is-ancestor`. This is staging-only, but staging is exactly what feeds the next promotion to master, so it needs fixing before that happens.

## Re-investigated 2026-09-02 (overnight deep run) — diagnosis corrected: the accept flow is NOT broken

The Summary and Suspected-cause sections above are superseded. The deep run traced both failure modes to their sources, read-only, and neither is an app regression in the /q accept flow:

**1. The accept persists fine.** Service-role read-back on deployed staging (sha `82dac7a`, the code every red run tested): the CI suite's own quotes `E2E-SENT-001` and `E2E-LATE-001` are `status: "accepted"` with `accepted_at` 2026-09-01T19:45:56Z / 19:46:03Z — stamped BY the red 82dac7a run itself. `acceptQuoteOnline` writes the status flip before any Zoho work (`lib/quote/accept-flow.ts:735`), and it landed.

**2. Failures 3–5 + the p0-money dialog (failure 2): the staging Zoho org ran out of API quota.** Both accepted rows above carry `zoho_deposit_error: "The API call for this organisation has exceeded the maximum call rate limit of 1,000"`. 2026-09-01 saw ~18 full e2e runs (the #171–#186 merge train and its QA/repair pushes), each hitting the staging Zoho org; the daily 1,000-call cap was exhausted somewhere between the green `710a832` run (14:32Z) and `cc42f50` (16:33Z). From then on every invoice-raising leg failed: no `-DEP` invoice (failure 3), no early balance so no £1,500 on the pay screen (failure 4), settle-in-full's raise errors so the radio stays (failure 5), and the office raise-balance dialog holds open showing the error (failure 2). External quota, not code — it resets daily.

**3. Failure 1 (lead stays "sent"): a spec race unmasked by #181, filed separately as QA-20260902-01 (`safe-fix`).** Staging's global `business_settings.card_payments_enabled` is `false`, so #181's new card-off sentence on the PRE-accept screen ("pay by bank transfer on the next screen…") satisfies the spec's `/Pay by bank transfer/i` landed-on-pay-screen sentinel instantly; the DB assert then races the in-flight accept action and reads `"sent"`. The accepts completed moments later — the failed runs' teardowns left behind contract `signatures` and deposit `follow_ups` only `acceptQuoteOnline` writes after the flip (5 orphaned `E2E-H3-HANDOFF-*` fixture sets, swept and verified 0 by this run). First red run = `076e46f`, the exact commit that introduced the copy; `710a832` immediately before it was green.

**Verified 2026-09-02T00:31Z — closed.** This run dispatched a fresh full CI run on `staging` (run id 33574683952, `4e87600` = `82dac7a` + qa/docs) against today's reset Zoho quota: **183 passed, 1 failed**. All four Zoho-dependent failures from this finding are GREEN on identical app code — `customer.spec.ts:37` (deposit invoice raised in staging Zoho), `customer.spec.ts:104` (late booking, both invoices), `settle-in-full.spec.ts:56`, and `p0-money.spec.ts:28` — proving the 2026-09-01 failure set was the exhausted Zoho quota, not the code. The single remaining red is `customer-accept-to-bookings.spec.ts:135`, failing on the same masked-sentinel race (status read back `"sent"` mid-action, no teardown FK error this time), which is the spec defect tracked as **QA-20260902-01** (`safe-fix`, for the repair loop). Nothing in this finding is an app defect; closed by the 2026-09-02 overnight deep run. The class stays `risky` only because the surface is payments — there is no app-code money defect left in this finding; the actionable remainder is the spec repair (QA-20260902-01) and an ops decision about the staging Zoho org's daily quota vs. the number of full e2e runs a busy merge day produces (~18 runs on 2026-09-01 — worth either a bigger org plan, fewer Zoho-gated runs per day, or an explicit "quota exhausted" skip in the Zoho-gated specs so a rate-limited run reads as SKIPPED, not as five spurious payment failures).
